## 3. System shape

Reflekt v1 is **one service** with **one bounded context** (Retrospective) and a Vue SPA bundled into the API's `wwwroot/`. Not a modular monolith: there is only one domain.

```
Browser (Vue 3 SPA)
   │  HTTPS + SignalR (WebSocket)
   ▼
Reflekt.API (ASP.NET Core + FastEndpoints + SignalR hub + cookie auth)
   │        (Features/ — endpoint classes, validators, IEvent handlers)
   │
   ├─▶ Reflekt.Domain      (aggregates, value objects, domain events)
   ├─▶ Reflekt.Persistence (DbContext, concrete repositories, SaveChangesInterceptor)
   │          │
   │          ▼
   │    SQLite (./data/reflekt.db)
   │
   └─▶ OpenGraph BackgroundService ──▶ outbound HttpClient (SSRF-filtered)
```

No RabbitMQ, no gRPC, no YARP, no MediatR. Domain events are FastEndpoints `IEvent` instances routed inside the process, published by a `SaveChangesInterceptor` after successful commit.

## 4. Solution structure

```
src/
  BuildingBlocks/
    BuildingBlocks.Domain/        # App-agnostic: AggregateRoot base, Entity base, domain-event marker
    BuildingBlocks.Persistence/   # App-agnostic: generic DomainEventPublishingInterceptor
  Services/
    Reflekt/
      Reflekt.API/
        Features/               # Feature slices — one folder per slice
          Teams/                #   Endpoint class + Request/Response records + Validator
          Sprints/
          Participants/
          Cards/
          Votes/
          EvidenceLinks/
          Reports/
        Events/                 # IEventHandler<T> implementations (SignalR broadcasters, fetch-job triggers)
        Hubs/                   # SprintHub
        Auth/                   # GuestTokenAuthenticationHandler, policies, AddReflektAuthentication extension
        OpenGraph/              # BackgroundService + Channel<FetchJob> + HTML parser + AddReflektOpenGraph extension
        DependencyInjection.cs  # AddReflektApi + UseReflektApi — composes the concern-specific extensions
        Program.cs              # Orchestration only: AddReflektPersistence + AddReflektApi, then UseReflektPersistence + UseReflektApi
        appsettings*.json
        wwwroot/                # Populated by Vite build
      Reflekt.Domain/
        Teams/                  # Team aggregate root
        Sprints/                # Sprint aggregate root + SprintPhase/SprintState VOs
        Participants/           # Participant aggregate root
        Cards/                  # Card aggregate root + EvidenceLink child entity + CardVote value object
        Events/                 # Domain event records (implement FastEndpoints IEvent)
      Reflekt.Persistence/
        ReflektDbContext.cs
        Configurations/         # EF Core IEntityTypeConfiguration per aggregate
        Repositories/           # Concrete repositories (no interfaces — CLAUDE.md rule)
        Migrations/             # Design-time, checked in
        DependencyInjection.cs  # AddReflektPersistence + UseReflektPersistence (migrate + seed, dev-only)
web/
  reflekt-web/                  # Vue 3 + Vite source; builds to src/Services/Reflekt/Reflekt.API/wwwroot
tests/
  Reflekt.UnitTests/            # Domain + endpoint logic unit tests
  Reflekt.IntegrationTests/     # WebApplicationFactory + SQLite in-memory/file
Reflekt.sln
docker-compose.yml              # Optional; SQLite file mount + env; not required for local dev
```

**`BuildingBlocks/` exists from day one** to house app-agnostic primitives that any serious DDD solution needs — aggregate root base class, entity base, and the generic domain-event dispatch interceptor. Two projects at Foundation time:

- **`BuildingBlocks.Domain`** — `AggregateRoot` base with `DomainEvents` collection, `Entity` base, domain-event marker (or re-export of FastEndpoints `IEvent` if we want runtime-free). Pure abstractions, no framework dependencies beyond the FastEndpoints abstractions package for the `IEvent` marker.
- **`BuildingBlocks.Persistence`** — generic `DomainEventPublishingInterceptor` (EF Core `SaveChangesInterceptor`) that walks any tracked `AggregateRoot` entities, calls `PublishAsync()` on each event, and clears the list. Knows nothing about Reflekt-specific aggregates.

No `BuildingBlocks.Application` project — FastEndpoints absorbs what would otherwise have been pipeline-behavior primitives. **App-specific** BuildingBlocks (gRPC contracts, integration event contracts per CLAUDE.md) stay deferred until v1 grows a gRPC surface or an event bus — currently it has neither.

**Rule for what belongs in BuildingBlocks:** if the primitive is > 2-3 lines AND has zero Reflekt domain knowledge, it goes here. Reflekt-specific primitives (the `GuestTokenAuthenticationHandler`, the OpenGraph SSRF-guarded HttpClient with Reflekt's timeout/limits, authorization policies that reference `Team.CreatorEmail`) stay inside `Reflekt.API`.

### Project reference graph

Per CLAUDE.md "Project reference graph":

```
Reflekt.API               ──▶ Reflekt.Domain, Reflekt.Persistence
Reflekt.Persistence       ──▶ Reflekt.Domain, BuildingBlocks.Persistence
Reflekt.Domain            ──▶ BuildingBlocks.Domain
BuildingBlocks.Persistence ──▶ BuildingBlocks.Domain
BuildingBlocks.Domain     ──▶ (FastEndpoints.Abstractions only — contract-level)
```

- `Reflekt.API` references `Reflekt.Domain` and `Reflekt.Persistence` directly (CLAUDE.md rule — no repository interfaces, no Application layer). It does **not** reference `BuildingBlocks.*` directly — it consumes primitives transitively through the domain/persistence projects.
- `Reflekt.Persistence` references `Reflekt.Domain` and `BuildingBlocks.Persistence`.
- `Reflekt.Domain` references `BuildingBlocks.Domain` (for the `AggregateRoot`/`Entity` base classes).
- `BuildingBlocks.Persistence` references `BuildingBlocks.Domain` so the generic interceptor can walk `AggregateRoot.DomainEvents`.
- `BuildingBlocks.Domain` depends only on the FastEndpoints abstractions package (for the `IEvent` marker that domain events will implement) — a contract-level dependency, not a runtime one.

## 5. Domain model

### 5.1 Aggregate boundaries

Split aggregates. Each row below is an aggregate root (AR). Reference across aggregates is by ID, never by navigation. Rationale: real-time retros mutate individual cards/votes hundreds of times per session; a big Sprint aggregate would force loading the entire retro state per mutation and invite write contention.

| Aggregate root | Scope key | Children | Raises |
|---|---|---|---|
| `Team` | — (root) | — | `TeamCreated` |
| `Sprint` | `TeamId` | — | `SprintCreated`, `SprintStarted`, `SprintClosed`, `PhaseAdvanced` |
| `Participant` | `SprintId` | — | `ParticipantJoined`, `ParticipantLeft` |
| `Card` | `SprintId` | `EvidenceLink` (child entity) | `CardCreated`, `CardUpdated`, `CardDeleted`, `EvidenceLinkAttached`, `EvidenceLinkFetched` |
| `Vote` | `(SprintId, CardId, ParticipantId)` | — | `VoteCast`, `VoteRetracted` |

`EvidenceLink` is a **child entity** of `Card`, not an AR — its lifecycle is the card's. The async OpenGraph fetch mutates the link via the owning `Card`.

### 5.2 Invariants enforced in Domain (not API, not DB)

- `Sprint` transitions: only `Draft → Active`, `Active → Closed`. No reopen. Phase transitions `Writing → Voting → Discussing → Closed` enforced by `Sprint.AdvancePhase()`.
- `Card`: `AssigneeName` non-null iff `CardType == ActionItem`; cards in `ColumnType.ActionItems` must be `CardType.ActionItem` (and vice-versa — the column ↔ type pair is coherent).
- `Vote`: rejected when `Card.CardType == ActionItem` (spec §5.3, §8).
- `Sprint.Close()` does not purge data; API layer enforces read-only for closed sprints by denying mutation commands.
- `VotesPerParticipant` checked at the API/handler level, not the aggregate level (a Vote doesn't know about the sprint's budget without loading sibling votes — keep this check in the handler with a count query).

### 5.3 Domain events

Dispatched via FastEndpoints `IEvent` after `SaveChangesAsync`.

**Raise:** aggregate methods append event records (which implement FastEndpoints `IEvent`) onto a `DomainEvents` collection on the aggregate root.

**Dispatch:** a `DomainEventPublishingInterceptor` (EF Core `SaveChangesInterceptor`) runs after a successful commit. It walks every tracked aggregate's `DomainEvents` list, calls `ev.PublishAsync()` on each, then clears the list. Chosen over per-endpoint explicit publish so no endpoint can forget to dispatch — every save flushes events exactly once.

**Handle:** `IEventHandler<T>` implementations in `Reflekt.API/Events/` (and optionally colocated with their feature slice). Two categories in v1:
- **SignalR broadcasters** — one handler per event that translates domain events into `SprintHub` pushes. Owns `IHubContext<SprintHub>`.
- **Evidence fetch trigger** — `EvidenceLinkAttachedEvent` handler enqueues a fetch job onto the OpenGraph `Channel<FetchJob>`.

No MediatR, no MassTransit, no outbox — single-process, cookies + SignalR group targeting is sufficient.

### 5.4 Forward-compatibility hooks (per spec §2)

- `Card.CardType` is an enum that will accept `AgentAuthored` later — define the enum open to extension; do not special-case in domain methods.
- `ParticipantId` on `Card` and `Vote` is a typed reference — when v2 introduces agent authorship, agents get their own `Participant`-shaped identity.

## 6. Feature slices (in `Reflekt.API/Features/`)

Each feature folder contains one FastEndpoints endpoint class (owns the handler method), its request + response records, a sibling `Validator` class, and a Mapster mapping config if needed. No service classes, no "helpers" folders, no separate command/handler split.

| Slice | Endpoints | Notes |
|---|---|---|
| `Teams/` | `CreateTeam`, `GetMyTeams` | Google-auth required. Allowlist check. |
| `Sprints/` | `CreateSprint`, `StartSprint`, `AdvancePhase`, `CloseSprint`, `GetSprint`, `GetTeamSprints` | SM-only for mutations; participant or SM for `GetSprint`. |
| `Participants/` | `JoinSprint`, `GetCurrentParticipant` | Endpoint issues/returns guest token. |
| `Cards/` | `CreateCard`, `UpdateCard`, `DeleteCard`, `GetSprintCards` | Ownership check (own-or-SM) in the endpoint handler. |
| `Votes/` | `CastVote`, `RetractVote` | Budget check via count query. Rejects Action Item cards. |
| `EvidenceLinks/` | `AttachEvidenceLink`, `DetachEvidenceLink` | Fetch job enqueued by the `IEventHandler<EvidenceLinkAttachedEvent>`, not by the endpoint. |
| `Reports/` | `GetSprintReport` | Read-only projection; works on Active and Closed sprints. |

Cross-cutting flow for every mutation endpoint: FastEndpoints auto-runs the sibling `Validator` (FluentValidation) pre-handler → endpoint executes the handler → repository `SaveChangesAsync` → `DomainEventPublishingInterceptor` flushes `IEvent`s → response returned. Logging is a FastEndpoints post-processor registered globally in `Program.cs`.

## 7. Cross-cutting concerns

### 7.1 Identity & authorization

Two authentication schemes, composed:

| Scheme | Who | Storage | Used for |
|---|---|---|---|
| `Cookies` (backed by `Google` OAuth) | Team creator / Scrum Master | ASP.NET auth cookie | `/api/teams/**`, sprint creation/start/close/phase endpoints |
| `GuestToken` (custom `AuthenticationHandler`) | Participants | Header `X-Guest-Token` (GUID); mirror in SignalR access-token query param on handshake | Card/vote/participant endpoints, SignalR hub |

Both schemes can authenticate the same request. Authorization policies:
- `ScrumMaster` — requires `Cookies` identity AND `Team.CreatorEmail == user.email` for the target team.
- `Participant` — requires `GuestToken` identity AND `Participant.SprintId == target sprint`.
- `OwnerOrScrumMaster` — used for card edit/delete: passes if caller is the card's `Participant` OR Scrum Master of the sprint.

Email allowlist (spec §12.6): in `appsettings.json` under `Auth:AllowedEmails`. Enforced after Google sign-in; unlisted emails get a friendly "not invited" page, no team row created.

### 7.2 Real-time (SignalR)

- **One hub**: `SprintHub` at `/hubs/sprint`.
- **Groups per sprint**: clients call `JoinSprint(sprintId)` on connect; server adds them to SignalR group `sprint:{sprintId}` after verifying guest-token → participant → sprint match.
- Server never calls clients directly — every push goes to a group.
- Events match spec §7.1 exactly: `CardCreated`, `CardUpdated`, `CardDeleted`, `VoteCast`, `VoteRetracted`, `PhaseChanged`, `ParticipantJoined`, `ParticipantLeft`, `EvidenceLinkFetched`.
- Pushes are fired from FastEndpoints `IEventHandler<T>` implementations in `Reflekt.API/Events/` — they own `IHubContext<SprintHub>`. `Reflekt.Domain` and `Reflekt.Persistence` never reference SignalR.

### 7.3 OpenGraph fetch pipeline

```
AttachEvidenceLink endpoint
   │ save EvidenceLink with FetchStatus=Pending
   │ Card aggregate raises EvidenceLinkAttachedEvent (IEvent)
   │ SaveChangesInterceptor publishes after commit
   ▼
ChannelWriter<FetchJob>  ◀── IEventHandler<EvidenceLinkAttachedEvent>
   │
   ▼
OpenGraphFetcherService (BackgroundService)
   │ HttpClient with 5s timeout + SSRF guard (reject localhost, private ranges, non-HTTP(S))
   │ AngleSharp parses OpenGraph tags
   ▼
Update EvidenceLink (FetchStatus=Ok|Failed, Title/Desc/Image/Icon)
   │ Card aggregate raises EvidenceLinkFetchedEvent
   │ SaveChangesInterceptor publishes after commit
   ▼
IEventHandler<EvidenceLinkFetchedEvent> → SignalR group push to sprint:{sprintId}
```

One `BackgroundService`, one `Channel<FetchJob>`, bounded capacity. On failure: set `FetchStatus=Failed`, store no metadata (spec §6.2), no retry.

### 7.4 Persistence & migrations

- Single `ReflektDbContext`. EF Core configurations per aggregate in `Persistence/Configurations/`.
- Cascade-delete on `Sprint` set via `OnDelete(DeleteBehavior.Cascade)` (spec §4 note, even though v1 doesn't delete sprints).
- SQLite file at `./data/reflekt.db`, path configurable via `appsettings.json` (`ConnectionStrings:Reflekt`).
- **Migrations:** design-time, committed to the repo under `Reflekt.Persistence/Migrations/`. **Auto-apply on startup in Development only** — `app.Services.GetRequiredService<ReflektDbContext>().Database.Migrate()` behind `if (app.Environment.IsDevelopment())`. Production requires explicit `dotnet ef database update`.
- **Seed data (spec §12.7):** dev-only `DbInitializer` run on startup in Development after migration: one test team, one active sprint, 2–3 participants, a handful of cards. Toggleable via config (`Seed:Enabled`).

### 7.5 Error handling & validation

- FluentValidation validators are auto-discovered and executed by FastEndpoints before the handler runs. On failure, FastEndpoints emits RFC 7807 problem+json with field errors out of the box — no custom middleware.
- Authorization failures return 401/403 as usual.
- Ownership failures (editing someone else's card) return 403 with a domain-specific code via `SendForbiddenAsync` or `ThrowError`.
- No custom exception hierarchy yet — add it when the second service arrives (keeps v1 scope tight).

### 7.6 OpenAPI

- `Microsoft.AspNetCore.OpenApi` for the document, **Scalar** (`Scalar.AspNetCore`) for the interactive UI.
- Both registered in `Program.cs`; UI endpoint gated to `IsDevelopment()` per CLAUDE.md.
- No Swashbuckle.

## 9. Port convention

App prefix `40`. Reflekt is service index `1`.

| Protocol | Container port | Host port | Status |
|---|---|---|---|
| HTTP | 8080 | **4001** | mandatory |
| HTTPS | 8081 | 4041 | opt-in — not activated in v1 dev |
| gRPC | 8082 | 4051 | **not exposed** — Reflekt has no gRPC surface in v1 |

Recorded here per CLAUDE.md's "services do not duplicate port numbers in their own CLAUDE.md" rule — service's own CLAUDE.md (if/when added) records only the service index `1`.

## 10. Frontend (Vue 3)

- Source in `web/reflekt-web/` (outside the API project).
- Vite `build.outDir = ../../src/Services/Reflekt/Reflekt.API/wwwroot` (and `emptyOutDir=true`).
- `Reflekt.API` serves `wwwroot/index.html` for the SPA fallback route.
- Pinia stores:
  - `authStore` (cookie session for SM)
  - `sprintStore` (sprint state, cards, votes — hydrated on mount + reconciled via SignalR)
  - `guestStore` (guest token, display name; persists to localStorage under `reflekt:sprint:{sprintId}:token`)
- Tailwind only; shadcn-vue acceptable per spec §12 styling note if component coverage matches without heavy runtime.

## 11. Testing strategy

| Layer | Tooling | What it covers |
|---|---|---|
| Domain unit tests | xUnit, FluentAssertions | Aggregate invariants: sprint state machine, card type/column coherence, vote-on-action-item rejection |

Not in v1: load tests, mutation testing, visual regression.

## 12. Deferred items (out of scope for v1 architecture)

Flagged now so they're not silently added during implementation:

- MediatR (replaced by FastEndpoints' built-in event bus + validation)
- MassTransit + RabbitMQ integration events (no consumer)
- gRPC contracts (no second service)
- YARP API gateway (single service)
- Exception hierarchy + middleware (premature)
- Repository interfaces (CLAUDE.md guardrail; revisit only if mocking pain emerges)
- Docker compose for production (dev-only SQLite file is sufficient for v1)

## 13. Open questions deferred to implementation

Low-risk decisions the implementer can make:

1. Whether request/response/validator live in one file or three, inside the feature folder. FastEndpoints supports both; pick whatever reads better per slice.
2. Mapster vs hand-written mappers for the `Reports` slice — a judgment call; either is fine.
3. Shape of `FetchJob` DTO passed through the channel (internal, can change freely).
4. Whether `GuestTokenAuthenticationHandler` also issues a short-lived SignalR access token or reuses the header — pick based on the SignalR client's ergonomics.
5. FastEndpoints OpenAPI (`FastEndpoints.Swagger`) vs `Microsoft.AspNetCore.OpenApi` (§8 default). Default stands unless the MS package has gaps.
