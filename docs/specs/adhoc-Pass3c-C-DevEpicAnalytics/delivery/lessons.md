## Architect Lessons

- **Phase 1 (analyze) findings recorded before plan written.** This pass is the third sibling of the 3c-A/3c-B clean-break migration (computation → Domain, ADR-005/010). The shared kernel (`MetricCardData`, `MetricCardBuilder`) and shared wire types (`MetricCard`, `SparklinePoint` in `GetSprintSummary`; `SprintSummaryItem` in `DeveloperThroughputService`) already exist — 3c-C **consumes** them, creates nothing shared.
- **The 3c-C-specific complexity is cross-service shared structural records**, not metric cards. 3c-B's card types were per-feature; 3c-C has two genuine cross-service clusters: `SprintSummaryItem` (Throughput↔QaWorkload) and the DeveloperProgress structural records (Progress↔Detail). This is the one place the 3c-B plan template does not map 1:1 — surfaced as Q1.
- **Two of the seven endpoints (DeveloperQuality, QaWorkload) already have a separated wire layer with hand-written mappers** — their migration is lighter (move result records to Domain, re-point mapper) than the other five (which need new `*Response.cs` + Mapster). Surfaced as Q3 so the developer doesn't redundantly Mapster-ify working byte-stable mappers.
- **No gRPC adaptation in 3c-C** (unlike 3c-B). The 7 services are each consumed by exactly one endpoint; gRPC uses only ScopeChange+CarryOver (3c-B). QaTrends endpoint injects `BugRatioCalculator` (3c-B) — that wiring must be preserved through the QaTrends migration.

### Phase 2 (plan) decisions — user-overridden
- **Q1 → Option B (NOT my recommended A).** User chose the shared API-layer wire file (`SharedAnalyticsWire.cs`) over per-endpoint duplicated wire declarations. Plan Step 1 builds it; single-ownership enforced by grep in Steps 10/11. My A recommendation (vertical-slice purity) lost to the user's preference for no-duplication — a legitimate trade I should weight more evenly next time rather than defaulting to slice-purity.
- **Q2 → "most meaningful suffix" (NOT blanket `*Calculator`).** User rejected uniform `*Calculator`. I assigned per-class semantic suffixes as binding contracts: Throughput→`Calculator`, Progress→`Analyzer`, Detail→`Calculator`, Quality→`Scorer`, Epic→`Analyzer`, Workload→`Analyzer`, Trends→`Analyzer`. This actually re-aligns the project with the `analytics-computation-service` skill's intent (name by what it computes) — so the "skill vs project" divergence I flagged in Phase 1 is now *partly resolved by the user's choice*, leaving 3c-A/3c-B (all `*Calculator`) as the inconsistent ones, not the skill.
- **Q3 → keep hand-mappers** for DeveloperQuality + QaWorkload (matched my recommendation). Mapster-uniformity is a LOW follow-up.

### Plan review (critic Mode-2, code-grounded) — outcome
- **APPROVE, 1 LOW + 4 advisories, no HIGH/MEDIUM.** Code-grounded critic earned its keep on a doc-only-blind class: **LOW-1** caught my early-return counts (Throughput=1 not 2, Progress=2 not 3) — a fact only source-reading verifies; I had eyeballed them. Lesson: when a plan cites "N early returns at line X", that count must come from a grep, not from memory of the read.
- **My two lowest-confidence risks (QaWorkload + DeveloperQuality sparkline domain types) were resolvable without a question** — the critic confirmed the wire `SparklinePoint` and the domain points are field-identical and that the 3c-A pattern is "each calculator owns its own domain sparkline point." I had flagged them as "may need a user question"; they were actually decidable from the 3c-A precedent. Lesson: before deferring a sparkline/card-type decision to a question, check whether the prior-pass precedent already fixes the pattern (per-calculator-local, no cross-reuse). Folded as decided into Steps 5/7 + a new Step 11 grep (N1) guarding against cross-calculator reuse.
- **A3 dead-code catch:** `QaWorkloadResponse` (service line 97) is unused today — the endpoint builds `QaWorkloadResponseDto` directly. My plan said "stays wire-only / don't mirror to domain" (correct action) but implied it survives; the critic clarified it's deleted with the service file. Lesson: distinguish "wire-only, endpoint-assembled" from "dead, deleted" — both avoid the domain, but the disposition in the rename table differs.

### Step 1 done-check — outcome
- **PASS** — developer self-transitioned all 11 steps in one spawn (clean plan), independent build GREEN, all 10 critical invariants verified by **grep against source** (not self-report). The grep-driven done-check earned its keep: I confirmed INV1–INV10 directly rather than trusting `implementation.md`'s self-table — the right discipline for a wire-stability-critical refactor.

Lesson: an architect's "Step 11 verification sweep" doubles as the done-check's grep script — write it precise enough to run verbatim.
