# adhoc-ReflektIdentityUnification (RA2) — Lessons

## Developer Lessons

### Phase-1 analyze (re-grounding against committed RA1, HEAD 4d93287)

- **Plan's "Grounded facts" were written against RA1's *planned* end-state and diverge from committed RA1 in framing, not just confidence.** The plan said RA1 "already stopped calling" Reflekt's `User`/auth and that RA2 just "deletes them." Committed RA1 actually **kept** the `User` aggregate, `UserRepository`, `UserConfiguration`, `Users` DbSet, `JoinWithGoogle` factory, and `DbInitializer` seed-`User` — it only **stubbed the four login endpoints** to dead `_ra1/unmapped/*` routes returning `Task.CompletedTask` and reduced `AuthenticationConfiguration` to guest-only. Net: Step 1's deletion targets all still exist (good — nothing already done), but the plan understated how much live code (seed, hub fallback, domain factory) still references `User`. Lesson: when a plan is written against a *planned* predecessor state, treat every "already done by predecessor" claim as unverified until grep-confirmed.

- **A "rename" step can be a semantic data-migration in disguise.** Step 3 ("`UserId`→`PersonId`, structurally identical logic") is syntactically a rename but **changes the id value space** of every ownership key: `GetUserId()` reads `NameIdentifier` = Identity **User** id today, repoints to `person_id` = Identity **Person** id. `Team.OwnerId`, the `{SprintId, UserId}` uniqueness index, and `SprintHub`'s owner comparison all silently change meaning. The grep-acceptance ("zero stale `GetUserId`/`.UserId`") catches the syntactic rename but **not** the semantic break. Lesson: for any FK/identity rename, ask "does the *value* in this column change meaning?" separately from "is the symbol renamed?".

- **`SprintHub.cs:204` reads `NameIdentifier` directly, bypassing `GetUserId()`.** A mechanical "repoint `GetUserId()`" misses call sites that read the claim inline. Lesson: grep the raw claim name (`NameIdentifier`), not just the helper, when repointing a claim's meaning.

- **Route-prefix scoping is unsafe when modules share a generic prefix.** Reflekt and Fokus both serve `/api/sprints/*`; there is no Reflekt-only prefix and no FastEndpoints `Group` discriminator. The plan's first-named Step-4 mechanism (route prefix) is not viable; assembly-of-declaring-endpoint is the robust discriminator. Lesson: before proposing route-prefix-based middleware scoping, grep sibling modules for prefix collisions.

- **One global FastEndpoints pipeline serves all three modules** (`Program.cs:20-28` single `AddFastEndpoints` assembly set; `:48-54` global pre-processor). The plan's "register the gate as a non-global pre-processor on Identity/Fokus groups only" has no per-module hook to attach to. Lesson: verify the composition topology (one pipeline vs per-module) before assuming per-module registration is available.

- **Subagent (Explore) findings stranded again** — both `Explore` agents returned `"Ignored"`/`"Ready"` placeholders, not findings (matches known MEMORY note). Direct Grep/Glob/Read was faster and reliable for this verification. Lesson: for load-bearing factual verification in this environment, prefer direct tools over spawned Explore agents.

- **The RA1 `InitialReflektSchema` migration is incremental, not from-scratch.** It layers audit columns onto tables created by the **lifted `<reflekt-repo>` migrations** (`AddTeam`…`AddReviewStatus`, still present), so the existing `reflekt.db` already has `Users` + `Participants.UserId` FK. Step 7's "drop Users / rename column" is valid against that base, but must also **drop the `ParticipantConfiguration` FK `HasOne<User>()` + `{SprintId, UserId}` index** (lines 24-25) — the plan says "rename column" without mentioning the FK to the dropped table. Recorded as a migration-correctness note for implementation.

## Architect Lessons

### Phase-1 adjudication of developer Q3/Q4/Q5 (re-grounding RA2 against committed RA1)

- **All three questions are technical, adjudicable from ADR-016/021/022 + code — none is a product/user decision.** Q3 (ownership value space), Q4 (pre-processor scoping mechanism), Q5 (seed owner) all resolve from the binding ADRs plus grep-confirmed source. The developer's recommendations (Person id everywhere; assembly-of-declaring-endpoint discriminator; drop the seed-User block + sentinel Person id) are all correct. No escalation needed. Lesson: a question that *cites an ADR and a code fact* is almost always architect-adjudicable; the escalation test is "does answering require a preference the ADRs don't already encode?" — here, no.

- **Q3's value-space flip is real but self-consistent through the shared helper — except the one bypass.** Confirmed by grep: 31 `GetUserId()` call sites, and every ownership comparison is `team.OwnerId != User.GetUserId()` (read side) while every owner write is `Team.Create(name, User.GetUserId())` (write side). Both sides flow through the *same* extension method, so repointing `GetUserId()→GetPersonId()` keeps endpoint comparisons internally consistent (new `OwnerId` and the compare value both become Person id). The break is isolated to `SprintHub.cs:204` (reads `NameIdentifier` directly, not via the helper) + stale pre-existing rows. So Q3(a)=yes, (b)=yes (repoint the hub fallback to `person_id`), (c)=yes (no backfill, dev DB disposable). Lesson: when a value-space flip threads through a single helper, the blast radius is the helper's call sites *plus* every raw-claim bypass — grep the raw claim name to find the bypasses.

- **Q4: assembly-of-declaring-endpoint (option A) is the ADR-021-correct discriminator; scheme-based (C) is NOT, even as a fallback.** ADR-021 explicitly requires the gate to pass an *authenticated Person-without-User* participant (the waiting-room case). Scheme-based skip (skip non-cookie principals) fails exactly that case because a waiting-room participant carries the Identity cookie. The plan listed (C) as an acceptable RA2 fallback "because RA2 has no such participants yet" — but adopting a known-forward-incompatible mechanism for a *seam the same pass is told to preserve* (ADR-021 "leave compatible plumbing") is self-contradictory. Recommend ratifying (A) as the RA2 mechanism, not a fallback. Lesson: a "temporary" mechanism that contradicts the very seam the pass is preserving is a debt the pass creates, not avoids — reject it at plan time.

- **Q5 couples to Q3 and resolves with it: drop the seed-`User` block, own the seed Team by a documented sentinel Person id constant.** The seeder is dev-only cosmetic (a demo board); ADR-022 + Q3's "no backfill" make a sentinel Person id the least-machinery answer. Confirmed the FK blast radius is wider than the seeder: `TeamConfiguration.cs:15` (`HasOne<User>()` for `OwnerId`) and `ParticipantConfiguration.cs:24-25` (`HasOne<User>()` + `{SprintId,UserId}` index) both reference the `User` type Step 1 deletes — the plan names neither. Both must drop in Step 7's migration. Lesson: removing an aggregate breaks not just code that reads it but every EF config with a `HasOne<That>()` relationship — grep `HasOne<{Type}>` / `HasForeignKey` before scoping a "drop table" migration.

- **ADR-016 vs the plan's "gRPC not needed in RA2" — refinement, not conflict, but should be recorded as an explicit ADR amendment, not buried in a plan's grounded-facts bullet.** ADR-016 says "Reflekt becomes a second `IPersonService` client." The plan defers that to the waiting-room feature (RA2 only *reads* the Person id from a new `person_id` cookie claim; it never *mints* a Person, so no gRPC client is needed yet). This is consistent with ADR-016's intent (Reflekt mints Persons only when it must, which is the waiting-room/guest-auth case) but the *letter* of ADR-016 reads as if the client lands in the unification pass. Lesson: when a plan refines an ADR's timing, the refinement belongs in the ADR register (a one-line amendment to ADR-016 or a note on ADR-021/022), not only in the plan — otherwise the next reader hits an apparent plan-vs-ADR conflict. Flagged to the team lead as an owner-ratification item.

- **Plan-completeness gaps found beyond the three questions (for Phase 2):** (1) Step 3 must add `SprintHub.cs` to its edited-file list and repoint `:204` to `person_id` (Q3b). (2) Step 3's rename touches the **wire-visible** `JoinSprintResponse(... int? UserId)` DTO at `ParticipantContracts.cs:3` — a serialized field rename the frontend consumes; the plan's "update every call site" must name this as a contract change (frontend is out of RA2 scope per the plan, so either keep the JSON name `UserId` while renaming the backing property, or flag the frontend break as a carry-over). (3) Step 7 must drop the two `HasOne<User>()` FK configs + the `{SprintId,UserId}` filtered unique index, not just "rename the column." (4) The seed-owner sentinel (Q5) needs to be a named constant with a dev-only comment. These are plan edits for Phase 2, not new questions.

### Phase-2 revision (rulings applied; owner chose critic review)

- **A "rename" plan step needs an explicit rename table + a wire-stability carve-out when ANY field it touches is serialized.** Step 3 renamed `UserId`→`PersonId` everywhere, but `JoinSprintResponse.UserId` is a JSON field the frontend reads. The grep-acceptance ("zero `.UserId`") applied literally would have *forced* a wire break. Fix: keep the serialized name `UserId` (pin with `[property: JsonPropertyName]`), rename only the backing property, and mark it a **sanctioned exception** to the grep rule in the plan so the done-check/critic doesn't flag it. Lesson: a global rename's acceptance grep must enumerate its serialized-name exceptions explicitly, or it becomes a self-inflicted wire break.

- **Removing an aggregate breaks every `HasOne<That>()` relationship config, not just code that reads the type.** Two EF configs (`TeamConfiguration:15`, `ParticipantConfiguration:24`) carried FK navigations to the deleted `User`; the migration would have failed the model-snapshot pending check. Folded the FK drops into Step 1 (config) + Step 7 (migration). Generalizable (belongs in the type-move plan rules): before a "drop aggregate/table" step, grep `HasOne<{Type}>` / `HasForeignKey` / FK constraint names — relationship configs are a separate blast surface from the type's own references.

- **A rejected option must be struck from the plan's Risks section, not just over-ruled in the answer.** The original Risks bullet still offered scheme-based scoping as "an acceptable RA2 fallback." Leaving it would let the developer fall to the rejected option under implementation pressure. Replaced it with an explicit "rejected — raise a new question instead" directive. Lesson: when adjudicating a multi-option question, edit *every* place the plan named the rejected option (steps AND risks), or the rejection leaks.

- **An ADR-timing refinement the plan discovers belongs in the ADR register as a one-line note — not left only in the plan.** Added the `IPersonService`-client-timing note to ADR-016 itself (owner-ratified), so the next reader doesn't hit an apparent plan-vs-ADR conflict; the plan cross-references it. Lesson: a plan that refines an ADR's *timing* (not its decision) carries a one-line amendment back to the ADR.

- **Edit-tool guard re-fires across a long resume/spawn boundary.** `plan.md`, `questions.md`, and `lessons.md` each required one fresh Read at Phase-2 start (the resume invalidated in-context file-state). Re-read each **once**, not per-edit — within Read-Discipline (which forbids the *per-cycle* re-read). Lesson: budget one re-read per artifact at a resume boundary.

### Critic round-1 fixes (the one that should not have shipped)

- **An acceptance grep MUST be derived by running the grep, never written from spot-inspection of the sites I happened to read.** This is the root cause of the whole REJECT. I wrote Step-3's acceptance as "`grep ClaimTypes.NameIdentifier` → zero hits, the SprintHub:204 bypass is gone" after *inspecting* two bypass sites (SprintHub + the DTO). The actual exhaustive grep returns **6** hits — including `GetSprintSummaryEndpoint.cs:25`, a **second owner-comparison** with the identical value-space bug Q3(b) exists to fix (CRITICAL: silent `isScrumMaster=false` for the real owner), plus `EditCard`/`DeleteCard` presence-checks. An acceptance criterion that prescribes a grep but is authored from inspection is **self-inconsistent by construction** — it states a zero the prescribed edits can't produce. The `create-implementation-plan` rule "a 'fix every file matching P' step must derive its list from the *exact* grep used in its acceptance" applies to **claim-read acceptance greps too**, not just file-list steps. Lesson (systemic): whenever a plan step's acceptance is a grep, **run that grep at plan time and paste the dispositioned hit table into the plan** — the table *is* the acceptance. I even found a 6th hit (`DeleteCard:61`) the critic itself missed — proof that only the exhaustive grep, not any inspection (mine or the reviewer's), is trustworthy.

- **A value-space-flip bug class recurs at EVERY raw-claim read that flows into the flipped comparison — enumerate the class by grep, don't catch instances by eye.** I caught `SprintHub:204` by inspection and *believed* it was the only helper-bypass. It was one of two owner-comparison bypasses. Lesson: once a value-space flip is identified, the defining query is "every `ClaimTypes.NameIdentifier` read that reaches a `team.OwnerId` comparison" — derive that set mechanically; spot-catching one instance creates false confidence that masks the rest.

- **"Re-grounded against committed RA1" must be literally true per file, not asserted in a header.** I claimed Step 1 was re-grounded, but the Step-1 deletion list still told the developer to delete `AuthenticationConfiguration.cs`'s cookie/Google registration — which committed RA1 had **already removed** (the file is guest-scheme-only, with a header comment saying so). A re-grounding claim that isn't carried into every step's *specific* targets is worse than no claim — it manufactures false confidence. Lesson: when stamping a plan "re-grounded against commit X", open each cited file at commit X and confirm the *specific* deletion/edit target still exists; a per-file diff, not a blanket assertion.

- **Dead code that references a renamed symbol is still in the rename's blast radius.** `JoinWithGoogle` and `GetByUserAndSprintAsync` have zero live callers but reference `UserId`, so they'd survive the rename as `.UserId` grep hits and block the acceptance. Resolved by deleting both in Step 1 (they're RA1 lift residue from the deleted Google-join path). Lesson: a rename/grep-acceptance must account for dead members carrying the old symbol — delete or rename them explicitly, don't assume "no callers" means "out of scope".

- **A "set X on the authed path" step is incomplete until it names the surviving endpoint + factory.** Step 6 described the *behavior* (set `PersonId` on authed join) but, after Step 1 deletes `JoinSprintGoogleEndpoint` + `JoinWithGoogle`, there was no endpoint/factory left for it to attach to — two developers would implement it differently. Fixed by naming the concrete RA2 shape: extend the single surviving `JoinSprintEndpoint` to read an optional `person_id` claim and call one `Participant.Join(…, int? personId)` factory. Lesson: a behavior-only step over a surface the same plan is deleting must state the *replacement* surface explicitly.

- **The critic was right and the fixes were genuinely mechanical — but the CRITICAL was a real, user-visible bug I'd have shipped.** The plan was "unusually well-grounded" on everything verifiable by reading (line refs, FK names, the 31-count, migration drops) yet still carried a silent-SM-corruption bug, because the one thing I did *not* mechanically derive (the acceptance grep) was the one thing that would have surfaced it. Lesson: groundedness on the parts you read does not cover the parts you inferred — the inferred acceptance is exactly where the defect hides.
