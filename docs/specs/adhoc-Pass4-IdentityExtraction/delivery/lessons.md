## Architect Lessons

- **Phase 1 analysis surfaced a load-bearing cross-module gap the spec left implicit (Q13).** The spec names exactly two sanctioned cross-module mechanisms (integration event Identity→Fokus for the seed; gRPC `PersonGrpcService` Fokus→Identity for Person upsert) but the **synchronous Identity→Fokus invitation validate-and-accept** that redemption requires is covered by *neither*. The architecture (`suite-integration-architecture.md` §154) restricts cross-module access to gRPC or integration events, and only gRPC is synchronous — implying a **second gRPC contract** (`IInvitationService`, Fokus server / Identity client) the spec never named. This expands "the cross-module Person service (new)" into **two** new gRPC contracts in opposite directions. This is a scope decision for the PO/user, not an architect call. Lesson for the PO: when a spec says "bridge across the boundary" for a *synchronous* flow, name the exact mechanism and direction, the same way Q8/Q9 did for the other two seams.
- **The critic Mode 1 spec review (1H/4M/5L) did not catch the redemption-mechanism gap** because it cross-referenced the 12 answered questions and the ADRs but did not trace the *synchronous round-trip* requirement of redemption against the available transports. Mode 1 verified "no ADR-001 violation" (true) but missed that the sanctioned mechanisms don't cover the synchronous case. Lesson: spec reviews for cross-module features should explicitly map each cross-boundary interaction (direction, sync/async, payload returned) to a named transport, not just confirm "a transport exists."
- **gRPC client infrastructure is absent in this repo (Q15).** Only `protobuf-net.Grpc.AspNetCore` (server) is in CPM; the client packages and a `Blocks.AspNetCore` client-registration helper do not exist (they exist only in the reference repo). Both gRPC seams therefore carry a **Build** disposition (build missing infra first, then follow the `create-grpc-contract` Client workflow) — not a plain Follow. The skill's Client workflow references `GrpcServicesOptions`/`AddCodeFirstGrpcClient` from `Blocks.AspNetCore`, which must be ported in first.
- **The `create-aggregate` skill is a partial fit for the User promotion.** User→AggregateRoot is a **type-change-in-place** on an existing entity (Entity<int> → AggregateRoot<int>), not a fresh aggregate scaffold. The skill assumes `Repository<T>` base + `AuditedEntityConfiguration<T>`; Identity uses plain repos + `IEntityTypeConfiguration` and a hand-written `UserConfiguration`. The in-repo pattern to mirror is the existing `Person` aggregate (state/behavior partial split, `RaiseCreated()` after save so EF has assigned the PK) — domain-patterns skill + Person as the example, with `create-aggregate` only for the EF-config shape.
- **The seed domain-extraction must byte-match the existing gate.** `CreateInvitationEndpoint.cs:21` extracts the domain as `email.Split('@')[1]` (case-insensitive compare). The auto-seed must use the *identical* extraction so the seeded value always matches what the gate later compares (spec BR 9 / critic L3). This is a concrete pattern reference to anchor in the plan, not a freeform "derive the domain."

### Plan-writing lessons (Phase 2)

- **The single-bus topology was the decisive wiring constraint, only visible from source.** Exactly one `AddMassTransit` (Fokus) and zero `AddConsumers` anywhere; Identity has no MassTransit package. The seed event therefore forced a Build step (Step 9): add `AddConsumers` to the *existing* bus (not a second `AddMassTransit`) and give Identity the publish dependency. A doc-only review would never see this — it is grep-on-disk knowledge. Reinforces: code-grounded review is mandatory for shared-infra passes.
- **The User-promotion migration was NOT ambiguous — I should have read the snapshot myself.** I hedged Step 1 ("may produce a migration iff…") and deferred resolution to the developer. The code-grounded critic (M1) read `IdentityDbContextModelSnapshot.cs` and proved it: Person (already an AggregateRoot) maps all four audit columns and nothing ignores them → promoting User WILL add four columns, mandatory. Lesson: when a base-class change's schema consequence is checkable from an on-disk model snapshot, the architect must check it during planning, not push a "diff and decide" hedge to the developer. The information was one Read away.
- **Two Build dispositions, both justified by verified-absent infra (not "no BuildingBlocks to reference").** gRPC client helper + CPM client packages (Step 3) and MassTransit consumer registration (Step 9). The skill's Client workflow assumes `GrpcServicesOptions`/`AddCodeFirstGrpcClient` exist in `Blocks.AspNetCore`; in this repo they exist only in the reference. Naming the exact reference file as the port source keeps it a Build, not an Adapt.
- **11 steps, kept unsplit — the dependency chain defeats a clean split.** Steps 1–6 are one prerequisite chain (promotion → contracts → client infra → both servers → redemption seam). Any seam-based split yields a sub-plan of <2 independent steps or introduces cross-sub-plan dependencies. Flagged the size to the team lead rather than forcing a split that violates the ≥2-independent-steps rule.
- **The "byte-identical extraction" rule mattered here too.** The seed domain derivation MUST be `email.Split('@')[1]` to match the Fokus gate (`CreateInvitationEndpoint.cs:21`); I anchored it with the exact file:line so the done-check is deterministic, per the refactor-plan-rules guidance.

### Step-1 done-check lessons

- **The code-grounded plan paid off at done-check: every flagged resolution (H1/M2/M3/L1/L2/L3/L5) was directly grep-verifiable in source, and all landed.** Because the plan named exact file:line anchors and binding invariants (e.g. `HasFilter("[Email] IS NOT NULL")`, "raise post-save", "`[DataContract]` not `[ProtoContract]`"), the done-check was a deterministic presence-check, not a judgment call. Lesson: a plan whose acceptance criteria are grep-shaped makes the done-check fast and unambiguous — keep writing acceptance as greppable facts.
- **Both developer deviations were *anticipated by the plan*, which made them trivially valid.** The migration-startup-project deviation was pre-named in the plan's Migration Notes ("or the Persistence-as-startup variant per `project-rules.md`"), and the Step-10-before-Step-4 reorder was forced by the plan's own dependency lines (Step 4 "Dependency: …, 10"). Lesson: when the plan declares the dependency graph and the known convention forks explicitly, the developer's reasonable deviations are pre-sanctioned and the done-check resolves them in seconds rather than escalating. Encoding the dependency order and the convention variant in the plan is what made the reorder a non-event.
- **My 3 pre-commitment predictions all missed (everything present).** I predicted the most-skip-prone items (Program.cs gRPC mapping, the SQLite filtered index, the Fokus CLAUDE.md half) — all were done correctly. Not a problem, but a calibration note: a well-fixed code-grounded plan removes exactly the gaps that predictions target, so on a post-critic plan the predictions should weight *novel* risks (e.g. the nullable-Email NRE in the new handler — which turned out null-guarded at `:50`) over the usual skip-suspects.

### Critic-cycle lessons (Mode 2, code-grounded)

- **The biggest miss (H1) was a cross-module *data-shape* assumption I never verified against the source.** I planned the Person upsert to match/require email without reading `JiraUser` (no email field) or `JiraDomainMapper.MapDeveloper` (maps only AccountId/DisplayName/avatar). The whole AC-8 "Jira developer → Person" flow was unachievable as written. Lesson: when a cross-module contract carries a field (email), trace that field back to its *actual source DTO* on disk before making it a key or a required field. A grep of `JiraUser` + `MapDeveloper` would have caught it in Phase 2. This is the load-bearing-fact-grounding rule applied to *data shape*, not just call sites.
- **I followed the skill's generic guidance over the verified in-repo precedent (M2).** I wrote `[ProtoContract]`/`ValueTask`/`CallContext` from the `create-grpc-contract` skill text, but the repo's `Blocks.Contracts` uses `[DataContract]`/`Task`/`CancellationToken` and references only `System.ServiceModel.Primitives` — protobuf-net attributes wouldn't even compile. The skill's "Follow = in-repo specifics differ" clause exists precisely for this; I should have read `SprintInfo.cs`/`ISprintCatalogService.cs` (I *had* read the latter in Phase 1) and matched it. Lesson: a Follow step's attribute/signature guidance must be reconciled against an actual in-repo example of the same artifact, every time — the skill is the pattern, the repo is the truth.
- **Three "if needed"/"may"/"either…or" hedges (M1, M3, M4/L4) were all resolvable from source.** The mandatory migration (M1), Identity's committed gRPC-server wiring (M3), and the exact client package + config shape (M4/L4) were each checkable on disk; I left them as developer-decides. Code-grounded review converted every hedge into a committed instruction. Lesson: a hedge in a plan is a deferred read — if the answer is on disk, resolve it in the plan; reserve hedges for genuine runtime unknowns.
- **A code-grounded critic earns its keep on shared-infra passes — exactly as predicted.** Every one of the 6 HIGH/MED findings was something only source-reading finds (DTO field absence, snapshot column mapping, contract attribute style, the ported helper's actual dependencies, the stale Fokus CLAUDE.md). A doc-only critic would have returned a near-clean pass. Reinforces the code-grounded-review-mandatory recommendation for shared/external-artifact passes.

## Skill Gaps

- No skill covers **promoting an existing Entity to an AggregateRoot in place** (the common DDD enrichment move) — distinct from scaffolding a new aggregate. Candidate for a `promote-entity-to-aggregate` skill or a `create-aggregate` variant. Recurs across the refactor program (User here; earlier passes promoted other types).
- The `create-grpc-contract` Client workflow assumes the `Blocks.AspNetCore` gRPC client helper already exists. When it doesn't (as here), the skill gives no guidance for the Build step (porting the helper + CPM packages). Consider a "client infra prerequisites" note in the skill.
