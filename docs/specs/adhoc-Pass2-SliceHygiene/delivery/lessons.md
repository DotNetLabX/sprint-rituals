# Pass 2 — SliceHygiene — Lessons

## Architect Lessons

- **Enumerate fat files with a definition-line grep, not a usage grep.** My first Step-3 list (14) was built from a broad `class .*(Request|Response|Validator|Dto)` scan that conflates *definitions* with *usages* (e.g. `EndpointWithoutRequest<MeResponse>` is a usage, not an inline definition) and also undercounted because I enumerated by memory of the files I'd read rather than a single authoritative grep. The correct count was 16. The precise pattern is `^\s*(public\s+)?(class|record)\s+\w+(Request|Response|Validator|Dto)\b`. The critic caught the 2-file gap (`GetDevelopers`, `GetCycleTimeBoundaries`). Lesson: for "split every file of class X" passes, derive the file list from the exact acceptance grep and make the two identical — never hand-curate the list separately from the check.

- **`EndpointWithoutRequest` features are still ADR-008 split targets even with no request type.** Three fat files (`GetTeamRoster`, `TestConnection`, `GetDevelopers`, `GetCycleTimeBoundaries`) are request-less reads that still define a response/DTO inline. The split moves the response/DTO to a `*Query.cs` sibling. Easy to miss when scanning for `*Request` types.

- **Mapster eligibility is narrower than "any hand-assignment."** ADR-010 says trivial mapping → Mapster, but the real boundary is *single-source object→object with name-aligned fields*. Method-dispatch handlers (`SetCapacity` calls `UpsertCapacityAsync(...)`), multi-source assembly (`UserResponse` from User + Person), and conditional logic (`SaveXraySettings` secret-preservation, `SaveCycleTimeBoundaries` stage-order) are NOT Mapster targets. A plan that says "replace hand-mapping with Mapster" without this carve-out will push the developer to force-fit `.Adapt` and break behavior. The strongest future-skill candidate is an `apply-mapster-mapping` skill encoding this eligibility test.

- **Wire-stability is a first-class plan concern when renaming contract types.** The MAXIMAL Q1 scope (rename gRPC/Jira `*Request`) is only safe because protobuf-net.Grpc keys the wire on `[DataMember(Order)]` and Refit serializes by property name — both decouple the wire from the C# type name. The plan must state the invariant ("don't touch Order numbers / property names") as a binding rule with a diff-based acceptance check, not assume the rename is mechanically safe.

- **Path-A field renames have a camelCase translation step the plan must spell out.** Renaming C# `AlertThreshold`→`BugRatioAlertThreshold` changes the wire JSON key to `bugRatioAlertThreshold`; the hand-written TS client payload must change to match. And the false-positive collisions (`workloadAlert.consecutiveSprintCount`, the cycle-time *response* read paths) must be explicitly fenced or a find/replace breaks unrelated code.

- **Done-check (Step 1) observations.** All 8 steps passed an independent grep-accept re-run + fresh builds (commit 3f07fa7). Two things worked *because* the plan made them explicit and grep-checkable: (a) the Mapster eligibility carve-out — the developer left `SaveXraySettings` (secret-preservation) and `SaveCycleTimeBoundaries` (stage-order) un-Adapted exactly as scoped; (b) the frontend false-positive fence — `workloadAlert.consecutiveSprintCount` survived the field-rename pass untouched. Confirmed: a grep-checkable acceptance criterion per step makes the done check fast and objective, and an explicit "do NOT touch X" fence prevents the find/replace collision a vaguer plan would have caused.
- **Plan-recommended-but-developer-deviated is fine when documented + consistent.** I recommended keeping the `SaveCycleTimeBoundariesResponse` keys stable; the developer renamed them and updated all consumers (TS type + Vue handler) together. Because the plan flagged it as a developer-time judgment (not a binding contract) and the developer documented the choice, it's a clean Deviated-with-reason, not a Missing/scope violation. Lesson: when a plan point is genuinely the developer's call, say so explicitly — it converts a potential "deviation" into a sanctioned decision and keeps the done check unambiguous.
- **The done check should hand the reviewer what a grep can't catch.** Conformance greps confirm the 5 `IRegister` maps exist and `.Adapt(existing)` is called — but only code review (or runtime) confirms `IgnoreNonMapped(true)` actually prevents `.Adapt` from nulling the ~20 untouched `AppSettings` fields (a real data-loss risk on a single flat row). I forwarded this explicitly to Step 2. Lesson: a done check should enumerate the data-integrity questions conformance verification structurally cannot answer, so the reviewer doesn't assume "PASS = safe."
  > **⚠️ ERRATUM (2026-06-07):** The premise of this lesson is itself wrong, and neither done-check nor reviewer caught it. `IgnoreNonMapped(true)` does **not** prevent nulling — it disables name-convention mapping, so a map with no `.Map()` calls writes **nothing**, making `.Adapt(existing)` a no-op. The 4 settings endpoints silently failed to persist (verified vs Mapster 7.4.0; `*Mappings.cs` deleted — see `adhoc-SettingsMapsterNoOp`). The corrected, generalizable lesson is below.

- **`IgnoreNonMapped(true)` is a whitelist, not a shield — and `.Adapt(existing)` never nulls unmatched members.** Two Mapster facts the whole pipeline got backwards: (1) `IgnoreNonMapped(true)` filters mapping to explicit `.Map()` resolvers only and turns OFF name-convention matching — with zero `.Map()` calls it maps nothing, so `.Adapt(existing)` becomes a silent no-op. (2) Mapster's default `.Adapt(onto existing)` already leaves destination members with no matching source untouched, so partial-update mapping needs **no** guard. Net: for a `Command → Entity` partial update where field names align, register **nothing** and just call `req.Adapt(existing)`. Process lesson: a "no-op write" bug is invisible to existence/shape greps AND to "does it leave other fields alone?" reasoning — the only verification that catches it is **save → reload → assert the value changed** (or a unit test on the mapping). Done-checks and reviews of write paths must include a positive-write assertion, not just a non-clobber argument.
