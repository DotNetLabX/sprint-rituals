## Architect Lessons

- **A triage `confirm` verdict must be re-verified against current source before planning a "fix."** B1 was logged `real (confirm)` against `Person.cs:30` ("RaiseCreated after SaveChangesAsync → never dispatches"). The current code (`AuthConfiguration.cs:106-107`) had already been restructured to raise-then-save-again, so `PersonCreated` dispatches today. Planning a "fix" for an already-fixed finding would have produced a no-op or a regression. Read the cited file AND its callers before trusting an aged triage line.
- **Adhoc-pass scope is reconstructed from the ADR register + triage, not invented — and three of four Pass-5 findings (B2, B6, B7/B1-redefine) carry unresolved `needs-decision`/`latent` verdicts that the architect cannot resolve unilaterally.** The User Decision Guardrail + the triage operating model ("needs a decision from the user") forced a questions-first checkpoint rather than a plan. The binding input for an adhoc pass with no `spec.md` is the backlog row + ADRs + triage; a one-line backlog row is not a scope.
- **Domain-event scope can be far smaller than the finding count implies.** Pass 5 reads as "4 findings" but the entire domain-event-dispatch surface is 2 events, 1 raise site, 0 handlers. `SprintSynced` (MassTransit integration event) and `SprintHub.SprintSynced` (SignalR method name) are NOT domain events — scoping them in would be a category error. Grepping `: IDomainEvent` / `AddDomainEvent(` / `IEventHandler<` up front bounded the work precisely and prevented over-scoping.
- **ADR cross-check surfaced a boundary conflict (Q5):** ADR-007 mandates rich aggregates including Identity, and B2's "wire UserCreated" resolution may require promoting `User` (an `Entity`, not `AggregateRoot`) to an aggregate — which is an encapsulation/ADR-007 question, not pure event-dispatch. Flagged as a scope-boundary question rather than silently folding an aggregate-promotion into an event-correctness pass.

### Phase 2 (plan-writing)

- **B7 is a genuine skill gap, verified two ways before setting `None`.** `persistence-patterns` documents `RepositoryBase.UpsertAsync` and even warns that `CurrentValues.SetValues` does not deep-copy **owned/complex** types — but it does NOT cover the **private backing-field** copy concern B7 names. The reference project (`<reference-repo>`) has **no `RepositoryBase`** at all, so there's no pattern to derive. Both the skill-frontmatter match and the reference-precedent check failed → `None` warranted.
- **B7's fix needed an explicit DO-NOT-TOUCH carve-out in the plan step** to keep it from sprawling: the backing-field copy (in scope) vs the owned/complex-type deep-copy (separate, already-documented concern, out of scope). Without the carve-out a developer "fixing SetValues" could try to solve both and over-reach into the owned-type assignment pattern.
- **A "fix-now" on shared `Blocks.EntityFrameworkCore` infrastructure needs its caller graph verified BEFORE writing a regression check — I skipped that and the critic caught it (F2, High).** I assumed Fokus's `SprintRepository`/`TicketRepository` "ride on the base" `UpsertAsync` and wrote a "sync the same sprint twice, confirm update" manual check. **Wrong:** all four Fokus repos declare `public new async Task UpsertAsync(...)` that *hides* the base and does explicit per-column copy; the sync services call the concrete types, so the `new` override resolves and the base method has **zero production callers**. The regression check I wrote tested a path the change can't reach. **Rule for next time: before asserting any end-to-end verification of a shared-base method change, grep for `public new {Method}` / overrides across all derived types AND confirm the call sites' static types — a `new`-hidden base method is dead code that no integration test can exercise.** This is exactly the create-implementation-plan refactoring rule ("enumerate ALL consumers from a grep before planning a change to a shared type") applied to method-hiding, which I under-applied because the method had obvious-looking consumers.

### Critic cycle (REQUEST CHANGES → fixes)

- **The code-grounded critic earned its keep: a doc-only review would have rubber-stamped F2.** The zero-caller fact is only discoverable by reading `RepositoryBase.cs` + all four `*Repository.cs` + the sync services. Recommending *code-grounded* critic review for a shared/infra-touching pass (not doc-only) directly caught a High framing defect. Reinforces the agent rule: shared/external-artifact passes need a code-grounded gate.
- **A latent/dead-code fix the architect recommended deferring, then the user overrode to "fix now," still needs honest value framing.** I had recommended defer (Q4); the user chose fix-now. The plan then over-claimed the fix "hardens the shared base" without noting the base is unreached. Honoring a user override is mandatory, but the plan must still describe the change's *real* (forward-only) value, not inflate it. Don't let "user said do it" turn into "so it must be valuable now."

### Done-check (Step 1)

- **Verified each step against committed source, not implementation.md — and it paid off on the one risky step.** Step 3's migration startup-project deviation was easy to wave through on the dev's prose, but reading the actual `Up`/`Down` `AlterColumn` (drops `oldDefaultValue: "Manager"`, restores in `Down`, preserves `maxLength/nullable`) and the snapshot's `Role` block (no `HasDefaultValue`, `IsActive` retained) is what *confirmed* the deviation produced correct output — a wrong startup project can silently scaffold nothing or the wrong delta. Disposition `Deviated (acceptable)`, not `Implemented`, because the command differed from the plan; PASS because the reason is valid and the output is correct.
- **A plan command can be the inaccurate artifact, not the deviation.** My plan (Step 3) specified `-s Identity.API`; the dev correctly used `-s Identity.Persistence` because Identity.API lacks `Microsoft.EntityFrameworkCore.Design`. The done-check should attribute the mismatch to the plan, not penalize the dev — and the dev's one-line `project-rules.md` clarification (commit `0ad86be`) is the right ADR-003 "fix the process" response. Lesson for plan-writing: when specifying an EF-migration command, verify the startup project actually carries the Design package before baking the command into a plan step.
- **A non-plan-step doc edit surfaced by an in-scope deviation is a boy-scout fix, not scope creep — but flag it for the reviewer rather than silently passing it.** The `project-rules.md` tweak isn't a numbered step; I passed it as an appropriate root-cause doc fix while explicitly routing it to Step 2 for confirmation (per the team-lead void context). The done-check's job is to classify and flag scope, not to silently absorb out-of-plan edits.

## Developer Lessons

- **`dotnet ef migrations add -s {Svc}.API` fails when the startup project lacks `Microsoft.EntityFrameworkCore.Design`.** `Identity.API` is a class library that does not carry the Design package — only `Identity.Persistence` does. When a Persistence project has both `Microsoft.EntityFrameworkCore.Design` and an `IDesignTimeDbContextFactory`, it should be used as both the `-p` and `-s` target. The `DesignTimeDbContextFactory` exists precisely for this scenario. **For future migrations in this service:** use `-p Services/Identity/Identity.Persistence -s Services/Identity/Identity.Persistence`. Update `project-rules.md`'s migration command example to note that the startup project must carry the Design package (or that the Persistence project can serve as startup when it has `DesignTimeDbContextFactory`).
- **EF `SetValues(PropertyValues)` vs `SetValues(object)` is a meaningful distinction.** When fixing `RepositoryBase.UpsertAsync`, the correct approach is `DbContext.Entry(existing).CurrentValues.SetValues(DbContext.Entry(entity).CurrentValues)` — the `PropertyValues` overload goes through EF's internal property machinery and respects configured `PropertyAccessMode`. Do not pass the detached POCO directly; `SetValues(object)` uses plain reflection and silently misses backing-field-mapped properties. This distinction is worth documenting in the conventions file rather than leaving it to code comments alone.
