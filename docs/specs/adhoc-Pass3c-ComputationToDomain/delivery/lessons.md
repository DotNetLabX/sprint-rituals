# Pass 3c — ComputationToDomain — Lessons

## Architect Lessons

- **Multi-consumer response records need explicit decomposition contracts before planning.** `SprintSummaryService.cs` defines records consumed by both the HTTP endpoint and `SprintAnalyticsGrpcService`. When migrating to domain result records, both consumers need updating — overlooking the gRPC consumer would leave it broken mid-migration. Always grep for record usages across the codebase before scoping the response-record decomposition.
- **Static utility classes also violate ADR-005 location rule.** `HealthScoreCalculator`, `TransitionAttributionChecker`, `CompletionChecker`, and `ExcludedDeveloperFilter` are static classes in `Fokus.API/Features/Analytics/` but contain pure domain logic. They are effectively domain helpers misplaced in the API layer. The plan must include moving these alongside the service-class migration.
- **`TestingCrunchFlag` is a cross-cutting domain type defined in `TestTimelineService.cs`.** Moving `TestTimelineService` to a domain calculator must also move `TestingCrunchFlag`, which is consumed by `SprintSummaryService` (pass-through to the response) and `SprintAnalyticsGrpcService`. Ordering: `TestTimelineCalculator` + `TestingCrunchFlag` domain type must land before `SprintSummaryCalculator` references it.
- **Plan split threshold:** 15 services + static helpers + response-record decomposition + gRPC adaptation well exceeds the 10-step split threshold. Phase 1 correctly surfaced the split question before writing an oversized plan.

### Done-check observations (3c-A)

- **A "grep before delete" sub-step in a plan must be a hard precondition, not a soft note.** Step 7's plan text said "before deleting, grep for remaining references" but did not make it a blocking checklist item. The developer skipped it and deletion exposed `MetricCard`/`SparklinePoint` + static-helper references in 22 files outside 3c-A's nominal scope (3c-B/C service files). The build was recoverable, but a phased pass that shares wire types across step boundaries should either (a) move the shared wire types in an earlier step with all consumers updated, or (b) make the grep a numbered verification sub-step the done-check can mark Missing. Promote to a plan-writing rule: when a refactoring pass deletes a file whose types are shared beyond the migrated feature, enumerate ALL consumers in the plan step, not just the ones in scope.
- **Cross-step shared-type migration in a phased plan leaks scope.** `MetricCard`/`SparklinePoint` lived in `SprintSummaryService.cs` but were consumed by 3c-B/C services. Splitting by computation-cluster (A/B/C) did not align with the wire-type ownership graph. Lesson for future split decisions: when choosing sub-plan boundaries, check shared wire/value-type ownership, not just which calculators cluster together. A type owned by the first-migrated file but consumed by later-migrated files forces transitional `using` churn.
- **Static-method-on-injected-class is an anti-pattern the plan inadvertently encouraged.** The plan told the developer to inject `TestTimelineCalculator` into `GetSprintSummaryEndpoint` AND to call `TestTimelineCalculator.ComputeCrunchFlag(...)` statically — producing an unread injected parameter (CS9113). When a calculator exposes a static helper, the plan should say "call statically, do not inject" or "make the method instance-level." Flag for the reviewer as LOW; promote to a plan-writing note: don't inject a dependency only to call its static members.
- **Wire-stability verification is fast and high-value when the rename table is explicit.** Because the plan gave an exact old-name→new-name table, byte-for-byte wire comparison was a direct field-by-field read. Keep the rename-table discipline for all future type-move plans — it makes the done-check deterministic instead of judgment-heavy.
