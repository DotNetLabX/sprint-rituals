# Pass 1 — SkillRepair — Lessons

## Architect Lessons

- **A "skill repair" pass has no in-repo artifact when the project is plugin-canonical.** This project removed all local `.claude/skills/` and relies on the shared, versioned plugin cache (`nexus-dotnet/0.1.1`). The pipeline (developer→repo, reviewer→repo diff, team-lead→repo commit) has nothing to operate on if the target skills live in the cache. Phase 1 must surface this as a blocker (Q1) before any plan — a plan that "edits the skills" would silently send the developer to write outside the repo, outside git, affecting every project on the machine. Decision-order: ask the user where the work lands before scoping it.

- **Verify proposal-era defects against the *currently installed* skill version before scoping repairs.** The `refactor-triage.md` / `skill-adherence-root-cause.md` proposals (written 2026-06-05) named defects that the plugin has since partly fixed: `create-aggregate`'s missing `workflows/*.md` now exist, and `persistence-patterns`' non-compilable `ref`/`HasDefaultValueSql` patterns are now documented caveats. Planning repairs from the proposal text alone would have scoped already-fixed work. Always grep the live skill files. Confirmed-still-present defects: `analytics-computation-service` returning response DTOs (conflicts ADR-005) and `domain-patterns` lacking the VO-vs-scalar rule (ADR-007).

- **A backlog row is not a scope. Pass 1's scope had to be reconstructed.** Unlike Pass 0 (which had a full scope section in `backlog.md`), Pass 1 is one table line. Scope was assembled from ADRs + triage skill verdicts + Pass 0 deferrals (`summary.md` line 20, `lessons.md` Skill Gaps). When the backlog defers detail, the architect reconstructs and *confirms* scope with the user rather than inventing it.

- **An explicit "user wants to review interactively" backlog flag is a hard checkpoint, not advice.** `backlog.md:38` reserves the `domain-service` skill shape for interactive user review. The reference project can't decide it either — the reference puts cross-aggregate logic in an Application layer that ADR-004 says this project doesn't have, so ADR-005 deliberately diverges (Domain-layer service). This is a genuine design fork the user reserved; the plan cannot finalize it (Q2).

- **The acceptance bar must be redefined when the deliverable is Markdown, not code.** Every prior pass gated on `dotnet build` green; Pass 1 has no compiler. The verification contract becomes ADR-mapping + anti-pattern/over-specification self-checks + "embedded code examples compile against this solution's BuildingBlocks." Flagged for user confirmation (Q4) so the done-check and review have a defined contract.

### Phase 2 (plan-writing) lessons

- **The user's actual answer can supersede the architect's offered options entirely — re-plan around the answer, don't force-fit it to an option.** Q1 offered A/B/C (project-local / upstream-spec-only / hybrid). The user chose *none of them*: skills are edited in a **separate editable plugin SOURCE repo** (`<plugin-repo>`), a keystone I hadn't enumerated. This made the plan a **two-repo** plan (artifacts here, skill edits there, separate commit targets) — a shape none of A/B/C described. Lesson: offered options frame a decision but don't bound it; read the answer for a better model than the ones offered.

- **A user instruction can rest on a false premise; investigate before encoding it as a step.** Q1's answer said "include a step to rebuild/sync the cache from source (inspect `scripts/` for a build/sync script)." Investigation showed `scripts/` has only `gen-commands.mjs` + `gen-omni.mjs` — **neither writes the install cache**. The cache is version-keyed and the marketplace points at GitHub, so the real sync is the `--plugin-dir` + `/reload-plugins` dev loop (per the plugin repo's own ADR-1/ADR-9). The plan encodes the dev-loop and explicitly *closes* the "find a build/sync script" instruction as investigated-and-refuted, satisfying the User Decision Guardrail (don't silently drop the instruction — show why it resolves differently).

- **Two-repo plans need the diff-location stated loudly and repeatedly.** `git status` in this project shows nothing for Steps 1–5; the diff lives in the plugin repo. The done-check and code review will look in the wrong place unless the plan headlines it. I put a "TWO-REPO MODEL — READ FIRST" section up top and repeated the plugin-repo path in every step's File line. Generalize: when a pass's deliverable lands outside the pipeline repo, make the foreign commit target a first-class, repeated callout — not a footnote.

- **The critic caught a real boundary half-covered: encode BOTH sides of a layering rule.** My first draft encoded ADR-005/010 (domain services *return* domain types, not response DTOs — the output side) but omitted ADR-006 (No DTO *enters* the domain — the input side). A `domain-service` skill silent on inputs could permit a calculator taking a `JiraIssueDto`. Lesson: a "boundary" rule has two sides; when a skill governs a boundary, audit input AND output, and cite every in-scope ADR (I had 6 of 7; ADR-006 was the miss). Critic Mode-2 against the ADR register (not just a spec) is the right gate for ADR-driven passes.

- **Critic ran in-context, not as an isolated subagent.** The team-coordination MCP (Agent/Task spawn) was disconnected this session, so I invoked the `nexus:critic` skill in my own context rather than spawning a separate reviewer. This violates the author≠reviewer separation principle in spirit. It still surfaced a substantive MEDIUM (ADR-006) and four LOWs, all applied. Flag: when subagent spawn is unavailable, in-context critic is the documented fallback but should be disclosed; a fresh-context re-review before Pass 1 *closes* would be stronger.

### Revision-cycle lessons (after fresh-context critic + Codex code-grounded review)

- **An in-context critic is structurally blind to whole CLASSES of defect that a code-grounded reviewer catches instantly.** My in-context critic returned APPROVE; the fresh-context critic returned GO-with-3-MEDIUM; **Codex (which read the actual skill files and the live repo) returned NO-GO with 6 HIGH.** The HIGHs were all things only source-reading finds: the analytics skill teaches API/Service framing in its *description/When-to-use/reference-table* (not just the one bullet I'd targeted — HIGH #4); a raw `SendAsync(` grep in this repo finds ONLY false-positives because `Send.*` is already dominant, so the naive detection is non-operational (HIGH #8); the repo escape-hatch as "inject repository interfaces" leaks `IRepository`/`IQueryable` into the Domain (HIGH #3); FastEndpoints is on **8.1.0**, not the reference's 7.x (C-1). Lesson: for a skill-repair pass whose correctness depends on the *current* state of shared files and the live codebase, an in-context or even fresh-context doc-only critic is insufficient — a code-grounded review (read the target files + grep the repo) is the load-bearing gate. Recommend code-grounded review as mandatory for any pass that edits shared/external artifacts.

- **"Skills are general/multi-variant" reframes every ADR-driven instruction.** My draft wrote ADR rules as absolutes ("since ADR-004 there is no Application layer…"). The user's D-A decision: these are SHARED multi-variant skills; ADR-004/011 are ONE variant. The fix is pervasive — every placement, DI, event-publisher, and `Send.*` rule had to become "light-stack variant (this solution) vs full-stack variant (reference)." Lesson: before encoding a project's ADR into a shared skill, ask "is this skill project-private or shared?" If shared, the ADR is a *worked example of one variant*, never the only way — and existing full-stack content is annotated, not scrubbed (HIGH #6 resolved by annotate-not-scrub).

- **A boundary rule can be too strict as well as half-covered.** The prior cycle's lesson was "encode both sides of the boundary" (added ADR-006 input rule). This cycle Codex showed the input rule I added was *too strict*: "domain types/VOs only" wrongly banned intrinsic computation primitives (`windowSize`, `anchorIndex`). Correct form: no external/integration/response DTOs enter the Domain; intrinsic primitives/enums are fine; VO when the input carries domain meaning. Lesson: when tightening a boundary, enumerate the legitimate non-DTO inputs so the rule doesn't ban necessary primitives.

- **D-B superseded an earlier "pragmatic" decision (Q2d).** Q2(d) said "avoid gratuitous DTO twins / reuse the domain type when 1:1." The user reversed it: the endpoint ALWAYS owns its own response contract + map, even 1:1, because the domain VO and the wire contract evolve independently. Lesson: "pragmatic minimalism" (reuse the type) trades a boundary for brevity; a later decision can re-prioritize the boundary. Record superseded guidance explicitly in the plan (I marked the old text "superseded") so the developer doesn't follow the stale rule from memory.

- **`improve-skills` has mandatory housekeeping (backlog/CHANGELOG/README) that the two-repo model re-routes.** The critic (C-2) caught that invoking `improve-skills` obligates `docs/skill-backlog.md` + per-skill `CHANGELOG.md` + `.claude/README.md` updates — which in this pass target the PLUGIN repo, not sprint-rituals, and the `.claude/README.md` one must NOT touch sprint-rituals. Lesson: when a Follow-skill mandates side-artifacts, the plan must state where those artifacts land under the active repo model, or the developer writes them to the wrong repo.

### Touch-up-cycle lesson (a fix can introduce a new defect — the variant framing did)

- **"Variant" is the wrong frame for two genuinely different patterns — a contrast section is.** Folding D-A (general/multi-variant skills) made me cast the reference's Application-layer `ArticleAccessChecker` as "the full-stack variant of `domain-service`." Codex flagged (new HIGH) that this is incoherent: that reference service depends on a `DbContext` directly, which violates the *same skill's* purity rule (pt3). Two patterns with contradictory rules cannot be variants of one skill. The fix was to scope `domain-service` to its one coherent pattern and demote the Application-layer alternative to a "see also / when this doesn't apply" CONTRAST — which still honors D-A (the skill doesn't claim the domain-layer form is the only way) without forcing two incompatible rule-sets under one name. Lesson: when applying a "support multiple variants" directive, first test whether the candidates actually share the skill's invariants. If a "variant" would break a rule the skill enforces, it's a *different skill/pattern* and belongs in a contrast/cross-reference, not a variant branch. Applying a generalization directive too literally can manufacture a contradiction the directive never intended.

- **Targeted touch-ups need a contradiction sweep, not just the edit.** After both fixes I grepped the whole plan for any residual "domain-service ↔ Application/DbContext" coupling to confirm the new contrast framing didn't leave a stale "variant" sentence behind. Lesson: for a fix that removes a conflation, the acceptance check is a repo-wide search for the conflated terms, not just re-reading the edited paragraph — the same wrong frame often appears in 3–4 places (map row, step body, DI, accept).
