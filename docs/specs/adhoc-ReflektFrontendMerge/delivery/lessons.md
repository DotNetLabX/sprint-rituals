# RA5-A — Lessons

## Developer Lessons

1. **PowerShell `Set-Content -Encoding utf8` writes UTF-8 BOM** — Node.js JSON parser rejects BOM-prefixed JSON files with a cryptic "Unexpected token '﻿'" error. Use `[System.IO.File]::WriteAllText(path, content, New-Object System.Text.UTF8Encoding $false)` for any JSON file that will be read by Node tooling. The `Write` tool (Claude's built-in) writes UTF-8 no-BOM correctly; only `Set-Content` has this footgun.

2. **npm workspace workspace-level dep hoisting vs app-level tsconfig paths must stay in sync** — when a workspace package (`@sprint-rituals/shared`) is introduced, three places must all agree: `package.json` dependency entry, `vite.config.ts` resolve alias, and `tsconfig.app.json` paths. Missing any one causes a build-time "module not found" or a type-check miss while the other succeeds silently.

3. **Copying in a source repo may surface pre-existing type bugs** — the Reflekt source had bugs (`hasTeam` vs `hasTeams`, `currentTeam` getter, 3-arg `createSprint` call) that were invisible in the source repo because its tsconfig was less strict. Enabling `noUncheckedIndexedAccess` in the copied app's tsconfig surfaced one more (`previousActions.ts` array index). Fix these at copy-in time; a broken build is not an acceptable hand-off.

4. **`@tsconfig/node24` is not a workspace-universal package** — the Reflekt source's `tsconfig.node.json` extended `@tsconfig/node24` which was not in the workspace root. Replace with explicit `compilerOptions` matching the in-repo pattern at copy-in time.

5. **When extracting a fetch call into a shared helper, carry the path prefix with it** — `apiFetch('/auth/me')` prepends `/api` implicitly in its `BASE_URL` constant. Extracting `fetch('/auth/me', …)` into a shared helper drops that prefix and the call silently routes to a non-existent path. Always trace where the full URL is assembled before extracting. The pattern: search the original caller's fetch wrapper for `BASE_URL` or path-building logic before writing the helper.

6. **When porting a source repo, cross-check every hard-coded auth path against the in-repo server** — the Reflekt source used `/auth/google/login` and `/auth/logout` which were correct against the Reflekt backend. The in-repo backend (Identity module) mounts `/auth/login` and `/api/auth/logout`. These are invisible at type-check time; they only fail at runtime. Audit all raw `window.location.href`, `fetch('/auth/…')`, and `?returnUrl=…` strings at copy-in time against the host server's actual endpoints.

## Architect Lessons

1. **Prescriptive Host-wiring steps survive contact better than "mirror the existing pattern."** Step 4's C2 fix worked because the plan named the exact replacement (two `RequestPath`-scoped `UseStaticFiles` + two prefixed `MapFallbackToFile` + registration-order constraint, with `Program.cs:51/76` line anchors) rather than saying "follow the existing fallback." There *was* no per-prefix pattern to mirror, and the critic caught that the bare fallback would 404 after the outDir move. Lesson: when a refactor invalidates the only in-repo precedent, the plan must spell out the new shape — a "follow existing" instruction would have produced a non-working augment.

2. **An all-`None` frontend/infra plan is a legitimate, clean done-check — the all-None exemption did its job.** No pattern skill covers npm-workspace restructure, Vite multi-build config, or ASP.NET per-prefix SPA fallback. The done-check scored skill conformance against the audit log scoped to the `developer:implement` token and found only the lifecycle skill — exactly as expected. No false "missing skill" finding. Confirms the exemption is correctly load-bearing for infra passes.

3. **Custom developer agent names skip the verify gate — re-run the builds, don't trust the self-report.** The `dev-ra5a` agent name meant the platform verify gate didn't fire, so the PASS rested on the architect re-running `dotnet build` + `npm run build` and grepping all cited file:line edits. Both were genuinely green. Lesson: when the verify gate is skipped (custom agent name, boundary-detector edge), the done-check must independently confirm build/conformance claims, never assume them. Worth flagging to the learner: a custom-agent-name → verify-gate-skip is a recurring operational seam (boundary-detector false-positive memory note is the sibling case).

4. **Plan-deferred "open question with a default" resolves cleanly at done-check when the default is stated in the step.** Step 4's cold-`/`-unauthenticated question carried `default = dashboard login` in the plan; the developer took the default and documented it. No escalation, one-line disposition. Reinforces the create-implementation-plan rule: a genuine developer-judgment point with a stated default pre-resolves what would otherwise be a deviation.

## Reviewer Lessons

1. **Shared type declarations must reflect the actual API contract, not the caller's wish.** The shared `AuthUser.givenName: string` is declared as required but `/auth/me` never returns it. The graceful `||` fallback in the consumer masked the runtime impact, but the type is a false promise. When reviewing a shared helper that wraps an API endpoint, always cross-check the declared type against the actual response DTO — not just the calling code.

2. **Type-unsafe casts that work at runtime are LOW, not ignored.** `authStore.ts` casts `sharedFetchMe()` to a richer local `AuthUser` type. The cast silences structural TS checking but is correct at runtime because the API does return the extra fields. The pattern is fragile (a future change to the shared type or the API response would break silently). File it as LOW and track for cleanup rather than elevating to MEDIUM/HIGH.

3. **Orphaned wwwroot root artifacts: trace the serving chain before calling them a risk.** `wwwroot/index.html` and `wwwroot/assets/` are orphaned build artifacts. Before flagging them as a security risk or routing hazard, trace: (a) is there an unscoped `UseStaticFiles`? (b) is there an unscoped `MapFallbackToFile`? Neither exists here — both handlers are prefix-scoped. The files are inert dead weight, not a routing hazard. Correct disposition: SAFE, cleanup follow-up.

4. **Raw URL strings in frontend code are build-invisible — always verify against the backend endpoint attribute.** `vue-tsc --build` green tells you nothing about whether `fetch('/auth/me')` matches `[HttpGet("/api/auth/me")]`. On any review touching cross-origin paths, read the actual server endpoint files and trace each raw URL string against the HTTP verb + route attribute. This is especially important on fix-cycle re-review where the developer has corrected paths but adjacent call sites may have been missed.

5. **Adjacent call sites near a fix are the first check in a re-review.** When a shared fetch helper's path changes, find every other call site that invokes the same endpoint via a different path-building mechanism (e.g., `apiFetch()` with its own `BASE_URL = '/api'`). Confirm those adjacent callers still route correctly — they may use a different convention that was not broken by the fix but could be affected by any shared-package refactor.

## RA5-C Developer Lessons (Phase 1 Analysis)

1. **Rename passes with acceptance greps must include ALL files the grep will touch, including the implicit ones.** The plan's Step 1 explicit repo rename list omitted `VoteRepository.GetParticipantIdsWithVotesInSprintAsync`, but the Step 1 acceptance grep (`rg "SprintId" src/Services/Reflekt --type cs -g '!**/Migrations/**' -g '!**/FokusSprint*'`) would catch `g.SprintId == sprintId` inside that method. The grep is correct; the list is incomplete. Before implementing any rename step, verify the acceptance grep against actual code to find implicit targets.

2. **Plan DTO counts derived from code need a code-grep baseline.** The plan stated "23 request/command DTOs" for Step 2, but code has 26. Minor count errors like this are common and harmless if the acceptance grep is the real gate, but the discrepancy needs architect acknowledgment before implementation to avoid a reviewer finding.

3. **Frontend scope for a route rename must include ALL callers — stores AND components.** The plan listed only stores (`{participant,vote,card,cardGroup,previousActions,sprint,report}.ts`) as Step 2 frontend scope. Code grep found an inline API call in `PreviousActionsPanel.vue:112`. Always grep `client/apps/retro/src` (not just `stores/`) when auditing route renames.

4. **Nested-prefix routes (`/api/teams/{teamId}/sprints/`) are a separate renaming surface from flat routes (`/api/sprints/`) — the plan's acceptance grep misses them.** The `sprint.ts` store has 7 calls to `/api/teams/${teamId}/sprints/…` that already 404 against the backend (which uses `retro-sessions`). These are outside the plan's stated scope and outside the acceptance grep, but they are broken today. Surface explicitly before implementing.

## RA5-C Developer Lessons (Phase 2 Implementation)

1. **Worktree agents work against a different baseline; verify before using their output.** A spawned worktree agent received files from the main tree, but the agent's internal edits targeted the wrong baseline (the pre-RA3 `SprintRepository` form). The correct approach: edit main-tree files directly (without worktree isolation) for large rename passes where the baseline is already partially applied.

2. **`HasColumnName("SprintId")` on a renamed property prevents EF from generating `RenameColumn` migration.** When a C# property is renamed (e.g., `SprintId` → `RetroSessionId`) and you add `.HasColumnName("SprintId")` to keep the old DB column name, EF Core sees "old name still in effect" and generates no migration. To get `RenameColumn`, remove the `HasColumnName` override entirely — EF detects the property rename automatically and emits the rename operation.

3. **The acceptance grep pattern `SprintId` (PascalCase) does not match camelCase local variables.** Local variable aliases like `claimSprintId`, `parsedSprintId`, and method parameters like `(int sprintId)` in hub methods are cosmetically stale but do not fail the `rg 'SprintId'` grep (which is case-sensitive and matches the PascalCase property/field identifier only). These can be cleaned up cosmetically in a follow-up but are not blocking.

4. **`FetchJob.SprintId` and `ParticipantContracts.SprintId` are non-obvious board-meaning hits.** The plan's explicit file list did not include `OpenGraph/FetchJob.cs` or `Features/Participants/ParticipantContracts.cs`. Always run the acceptance grep after completing the listed targets and before declaring a step done, to surface these implicit hits.

## RA5-C Architect Lessons (Done-Check)

1. **A flat-route grep count includes carve-out routes that share the new prefix — subtract them to reconcile a "27 vs 26" discrepancy.** The `/api/retro-sessions/` grep returned 27, but one was the RA4 `sprint-context` carve-out endpoint that was *born* with the `/api/retro-sessions/` prefix and never renamed in this pass. The 26 board-meaning routes renamed from `/api/sprints/` is the correct count. Lesson: when a rename pass and a prior carve-out share the same *new* prefix, the destination-prefix grep over-counts by the number of carve-out routes — always verify the *source* grep (`/api/sprints/` → zero) for the true rename count, not the destination grep. The developer's "27" in implementation.md was a benign prose label error (their own enumeration listed 26).

2. **A complete-rename endgame leaves one trap: an internal *type/namespace* family that shares the wire symbol's text but is not wire-visible.** The Step-3 accept grep `JoinSprint|LeaveSprint` was written to catch the **hub method** (wire), but it also matches the REST `JoinSprintEndpoint`/`JoinSprintCommand`/`JoinSprintResponse` types and the `Features.Participants.JoinSprint` folder — internal C# names, route already `/join`-renamed. The grep therefore does *not* return literal-zero even though every wire string is correctly renamed. Lesson for plan-writing: when "complete rename" is the endgame, the acceptance grep for a homonym like `JoinSprint` must either (a) scope to the wire surface (`\.invoke\("JoinSprint"`, hub method decl) or (b) the plan must explicitly state whether the internal REST type family is in or out of scope. An un-scoped substring grep over a homonym produces a non-zero that the done-check must hand-adjudicate — exactly the "non-call homonym" trap the create-implementation-plan refactoring rules warn about, here surfacing in the *acceptance* clause rather than the rename clause.

3. **A vacuous verify-gate pass (0 configured commands) means the done-check IS the build gate — re-run everything.** The verify gate recorded a pass with zero configured commands, so it proved nothing. The PASS rests entirely on the architect re-running `dotnet build` (green), `dotnet test ~Reflekt` (21 green), `has-pending-model-changes` ("No changes"), and `npm run build` (both apps green) — plus re-executing all three acceptance greps. Sibling to the RA5-A "custom agent name skips verify gate" lesson: whenever the verify gate didn't genuinely run (custom agent name OR zero configured commands), independent re-verification at done-check is mandatory, never assumed. Worth a learner note: the verify gate has at least two distinct silent-skip modes now.

4. **`RenameColumn` + standard SQLite FK drop/recreate is the correct migration shape — don't mistake the FK churn for column recreation.** The migration drops and re-adds the FK constraints (normal SQLite behavior, which can't alter a constraint in place) but the *column* operations are `RenameColumn`, so the data is preserved. `has-pending-model-changes` → "No changes" is the deterministic proof the rename is fully expressed. Lesson: when reconciling a "RenameColumn not drop/recreate" requirement, read the column ops specifically — adjacent FK drop/add is expected and is not a data-loss drop/recreate.

## RA5-C Reviewer Lessons

1. **A "complete rename" acceptance grep with a homonym substring does not return literal-zero even when all wire strings are correct.** The plan's Step-3 accept grep `JoinSprint|LeaveSprint` matches the internal REST type family (`JoinSprintEndpoint`, `JoinSprintCommand`, etc.) as well as the intended hub method target. The grep is the conformance gate for wire strings; internal type/namespace names that share the substring need a separate decision: are they in or out of scope? When the plan's endgame says "complete rename," the reviewer should explicitly rule on each residual internal-name family rather than relying on the grep to reveal it. Architect lesson: when writing the `Satisfies` grep for a rename pass, either scope to the wire surface (prefix + exact boundary) or state in the plan whether the internal type family is in scope.

2. **camelCase local vars that alias a renamed concept are cosmetically stale but functionally correct — they are outside the PascalCase acceptance grep and should not elevate to HIGH.** Variables like `claimSprintId`/`parsedSprintId` are local aliases assigned from `FindFirstValue("retroSessionId")` — they hold the renamed concept but are not the renamed identifier. The wire string is correct; the local alias is cosmetic. Rate as carry-over, not a finding.

3. **For rename passes where carve-out boundary spans hundreds of occurrences, verify both directions: source grep (old name) returns zero AND carve-out files are untouched.** The Step-1 acceptance grep confirmed zero board-meaning `SprintId` in Reflekt (non-migration, non-carve-out). A targeted grep of carve-out files confirms they are intact. Running only the source-zero grep is necessary but not sufficient — a mis-scoped rename could zero the source grep by renaming carve-out occurrences. The two-direction check (source → zero, carve-out → untouched) is the correct gate.

4. **A wire-key break is only caught by reading BOTH the send site and the receive site for byte-identical strings — a one-sided grep passes a broken contract.** The round-1 `ColumnConfigUpdated` BLOCKER (backend sent `sprintId`, frontend read `retroSessionId`) was invisible to a build (both compile) and to a one-sided grep (each side is internally consistent). The fix verification must read the C# anonymous-object key (`BroadcastColumnConfigUpdatedHandler.cs:14`) AND the TS payload destructure (`useRetroHub.ts:147`) and confirm they are byte-identical. When a rename moves a composable (`useSprintHub → useRetroHub`), re-confirm every paired wire key survived the move matched — a rename is a prime opportunity to re-break a just-repaired contract.

5. **A namespace/folder merge is "sound" only when proven by a green build + a clean `has-pending-model-changes`, not by file listing.** Step 5 merged `Features/Sprints/` into `Features/RetroSessions/` (collision resolution) while keeping the `GetSprintContext/` carve-out subfolder. Confirming the folder moved is not enough — broken `using`/namespace refs surface only at compile, and an accidental EF-config disturbance surfaces only in `has-pending-model-changes`. Verified sound by: zero `Features.Sprints` namespace decls remaining + green `dotnet build` + `has-pending-model-changes` → "No changes" + the carve-out subfolder's namespace unchanged.

6. **When scope expands mid-pipeline (wire-only → complete rename), re-anchor the verdict to the AMENDED plan and resolve prior findings against it, don't carry them.** My Cycle-1 MEDIUM (`JoinSprint*` internal type family deferred) became a Step-5 target in the amended plan and was implemented — so it is resolved, not a standing finding. A re-review after a scope amendment must re-read the plan's new acceptance gate (here the strengthened `rg -i "sprint"`) and treat it as authoritative, rather than re-applying the narrower cycle-1 gate.

## RA5-B Reviewer Lessons

1. **A fetch-once cache guard must be checked against BOTH halves of the plan clause: "once per session" AND "keyed by {id}".** The `sprintContext` store satisfied Rule 8 "fetch at most once" (a bare `loaded` boolean) but dropped the plan's "keyed by `retroSessionId`" half — so across a retro-A → retro-B SPA navigation the singleton store serves retro-A's data for retro-B. The done-check verified the guard against "fetch once" and passed; the behavioral half (per-id keying) is exactly what a Step-2 code review must trace. Lesson: when a plan says "cache keyed by X", grep the store for X in the guard condition — a guard that ignores X is a silent wrong-data bug, not a missing feature.

2. **In a Pinia SPA, a singleton store with a permanent guard and no `$reset` is stale-prone across route-param navigations — compare against sibling stores' refetch behavior.** The tell here: every other room-hydration store (`card`, `report`, `participant`, …) re-fetches unconditionally in `enterRoom()`, so they self-correct; `sprintContext` was the ONE store with a permanent fetch-once guard. When a store deviates from the established refetch pattern of its siblings, verify it resets or re-keys on context change. `rg "\$reset|loaded = false"` returning zero for a guarded singleton is the red flag.

3. **A done-check that verifies structure can pass a behaviorally-wrong cache — the Step-2 reviewer is the behavioral gate.** The Step-1 done-check correctly confirmed the `loaded` guard *exists* and the hydration locus is right, but "guard exists" ≠ "guard is correct across sessions". The two review steps are complementary: structure (done-check) vs behavior-trace (code review). Don't treat a thorough done-check as having covered cache-correctness.

4. **Verifying a keyed-cache fix means tracing the failure path AND the stale-flash window, not just the happy guard.** The Cycle-2 fix was correct precisely because: (a) `loadedFor` is set only inside `try` after the await, so a failed fetch leaves `loadedFor` ≠ the failed id → retry on re-entry; and (b) `sections = []` runs synchronously at fetch entry (before the await) while `loading = true`, so the panel shows the loading state during the cross-retro fetch and never flashes the previous retro's sections. A keyed-cache fix that set `loadedFor` before the await, or cleared `sections` only on success, would reintroduce a stale-flash or a non-retryable error. Trace both edges when signing off a cache-keying fix.

## RA5-B Developer Lessons

1. **The retro app uses Options API Pinia stores — the `pinia-patterns` skill prescribes setup stores but the codebase is Options API throughout.** When introducing a new store, match the existing app pattern, not the skill's template (which was written for the dashboard app). The key indicator: open any existing store (`report.ts`, `previousActions.ts`, `participant.ts`) and check whether they use `defineStore('id', { state, actions })` (Options) or `defineStore('id', () => { ... })` (Composition). Adapt the skill's async-action shape to the existing style.

2. **`defineProps` called twice in the same `<script setup>` causes a TS compiler error that vue-tsc does not always surface as a named-location error.** The first draft of `SprintContextSectionCard.vue` had `defineProps` both at the top and in the middle of `<script setup>` — an artifact of drafting in sequence. Always audit script blocks for duplicate macro calls before saving.

3. **When reading a retro-app type via `v-for item` with `key`, use `item.ticketKey` not `item.id` — `ScopeAdditionDto` has no `id` field (intentional: it exposes only `ticketKey`, `summary`, `storyPoints` per Rule 4 privacy invariant).** A `v-for :key="item.id"` on a `ScopeAdditionDto[]` would fail vue-tsc with "property id does not exist."

## RA5-B Architect Lessons (Done-Check)

1. **A "mount host" critic finding (H1) is verified by tracing the host's render condition to the panel's, not by confirming the host exists.** The button moved from `PageToolbar` to `RetroPhaseHeader.vue` — but "the button is on RetroPhaseHeader" only closes H1 if `RetroPhaseHeader` actually renders. The proof is the `v-else` chain in `RetroRoomView.vue`: header renders in the `joined===true` arm, and the panel renders on `v-if="joined"` as a sibling — so the button's host and the panel share the same mount gate. Done-check lesson: for a "wrong host" finding, read the *render condition* of the new host and confirm it is reachable in the relevant state, don't stop at "the component is referenced."

2. **A camelCase-wire contract done-check is a deterministic field-by-field table, not a judgment call — build the table from the DTO record and the TS interface side by side.** The panel binds to `GetSprintContextQuery.cs`; verifying "matches field-for-field" means literally pairing each C# record member to its camelCased TS field (incl. nullability: `decimal? StoryPoints` ↔ `storyPoints?: number | null`). The privacy invariant (Rule 4) is *structurally* held because `ScopeAdditionDto` has no assignee member — so the check is "confirm the absence in both," not "confirm the UI doesn't render it." Absence-in-the-contract is a stronger guarantee than absence-in-the-template.

3. **A "read-channel skill substitution" is a conformance PASS, not a skipped-skill finding — distinguish the invocation channel from the content.** Steps 1-3 carried non-`None` skills, but the Skill tool returned `Unknown skill` for all five nexus-dotnet frontend skills; the developer read each `SKILL.md` from the plugin cache and the pattern is visibly applied (L4/L3/L1 hierarchy, cache-once store, token classes). The done-check should verify the *skill content landed in the code* (it did) rather than failing the step for a missing Skill-tool log entry. This is distinct from the all-`None` exemption — here the skills were real and consumed, just via a fallback channel. Worth a learner note: a named developer agent appears not to get the nexus-dotnet frontend skills surfaced to its Skill tool (recurring with the developer's own skill-gap entry).

4. **Two pattern deviations that both reduce to "match the established app convention" are pre-sanctioned by the plan's grounding rules, not deviations to escalate.** The retro app has no `apiFetch` wrapper (raw `fetch` + inline guest headers) and uses Options API stores exclusively — so the developer's departures from the skill's dashboard-centric templates (`apiFetch` object, setup store) are the *correct* call. A done-check resolves these in one line as "Deviated (valid — codebase convention)" because the deviation aligns with existing in-repo precedent, which the plan's grounding rules make the binding reference for internal patterns.
