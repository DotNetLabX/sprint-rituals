# F11 — Publish Cleanup — Lessons

## Developer Lessons
- **Machine-path replacement: a bare repo root turned into prose doubles the wording when the sentence already names the repo before the path** ("reference project", "plugin source repo", "Fokus source repo" + the path). After a bulk replace, grep for `(project|repo|codebase) (the original|the reference codebase|this repo|the plugin source)` and fix those lines; also give command contexts (`git -C "…"`, `cd … &&`, code-block roots) placeholders, never prose. Cost here: a second cleanup pass over 8 lines in 10 files. **That grep was too narrow** — the review still found the class, and fix round 1 fixed 27 more lines: an article or adjective in front of the phrase ("the un-merged the original … repo", "the existing the original … client"), the phrase in front of a noun ("… project migrations"), a parenthetical repeating the name ("plugin source repo (the plugin source repo)"), "at this repo", a lower-case sentence start, and a bare command (`dotnet build X.slnx`) under a note saying the cwd is another checkout. What worked: a script that scans only the *added* lines of `git diff <baseline>` for those shapes, then reading every added line that holds a replacement phrase (about 110 here).
- **A cleanup that removes private tokens must check its own delivery record too.** I quoted one removed abbreviation in a step block and caught it only by running the step 3 search over `implementation.md`. Run the feature's token searches with `--untracked` over the delivery folder after writing each block, not only at the close.
- **`.claude/settings.json` cannot be edited in two stages:** the editor validates the file as Claude Code settings JSON after every Edit and refuses an intermediate invalid state. Remove keys by rewriting the whole file with one Write.
- **Name searches miss values that have a shape but no name.** The plan's token searches list known names, so an operator log that arrived after the build kept two public IP addresses, a subscription id, an application id and a cloud project name that no search listed. Add shape searches to a scrub's acceptance set from the start: IPv4 addresses, GUIDs (then sort cloud ids from tool session ids and documentation URLs), and the repo owner's login in `owner/repo` and `repo:owner/` forms. Operator and go-live logs are the densest source; read them line by line. **Evidence:** [F11-PublishCleanup]

## Architect Lessons

- Done check (light lane, cleanup feature): the coordinator's own `## Step 2 — Risky steps` line in `review.md` lists deleted file paths verbatim, so it re-introduced a removed private token into a delivery artifact. On a scrub feature, the risk recheck's `Unplanned:` list needs the same masking rule as every other delivery artifact. Otherwise only the close's `--untracked` sweep catches it. Worth filing as plugin feedback for `risk-recheck.js`: it has no redaction hook.
- **Search patterns in a cleanup plan self-match in more ways than a plain name.** Three slipped through here: a name inside an alternation list, a dot that matches a dot, and a phrase quoted as its own pattern. After writing the plan, run every search over the plan file itself with untracked files included, before the review. **Evidence:** [F11-PublishCleanup]
- **A worktree cleanup does not cover uncommitted work on the default branch.** The default branch held pending edits and untracked files with private names at the close. A publish-readiness plan lists the other checkout's pending work at plan time and owes a second sweep after the merge. **Evidence:** [F11-PublishCleanup]
- **Ask what was done before, first.** The owner had run this cleanup twice in sibling repos; three questions were withdrawn once those records were read. For a request that sounds like a repeat, search the sibling repos' feature records before putting any question. **Evidence:** [F11-PublishCleanup]
- **Read what the model repo did, not what its plans said.** The sibling repos' plan documents described a scrub on a fresh copy; the model repo's own state — its backup compared with its history, and the session that did the work — showed an in-place rewrite that kept every commit, date and author. When the owner names a repo as the model, compare its state before and after, then decide. **Evidence:** [F11-PublishCleanup]
- **`git filter-repo` drops a commit that becomes empty.** A commit that touched only removed paths disappeared, which would have broken the "every commit kept" promise. Pass `--prune-empty never --prune-degenerate never`, and compare the commit count and every commit's author, dates and message old against new before any push. **Evidence:** [F11-PublishCleanup]
- **Git Bash rewrites a path pattern that holds a slash.** A `--path-regex` argument was changed on its way to the tool, so the paths it named stayed in the history without any error. Set `MSYS_NO_PATHCONV=1` and `MSYS2_ARG_CONV_EXCL='*'`, and check after the run that each removed path is gone from every commit. **Evidence:** [F11-PublishCleanup]

## Reviewer Lessons

- Token searches catch only the spellings they list. On a scrub, also grep for sibling aliases of the private owner (a second tool-profile folder, a twin-plugin name) and for the deleted files' own names inside tool output pasted into delivery records.
