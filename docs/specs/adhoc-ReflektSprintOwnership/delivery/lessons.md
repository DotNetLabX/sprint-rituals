# adhoc-ReflektSprintOwnership (RA3) — Lessons

## Architect Lessons

### Phase-1 analyze (re-grounding RA3 against committed main, HEAD ca1ecd6)

- **The decisive scope fact was a *negative* one found only by sweeping the frontend: there is no Reflekt frontend in this repo.** `client/` is the Fokus dashboard SPA; its `/sprints` routes are Fokus analytics, not Reflekt. The Reflekt Vue app is still in the un-merged original Reflekt project repo (RA5 is Blocked). This single finding collapses the entire wire-stability question from "RA3 will break the frontend" to "RA3 has no in-repo wire consumer — stability is a future-RA5 concern." Lesson: on a rename pass, the highest-leverage early grep is "who actually consumes the wire surface in *this* repo" — a verified absence of a consumer reframes the whole risk model, and the backlog/ADRs won't tell you the consumer is in a different, un-merged repo.

- **`Sprint` is a three-meaning homonym in Reflekt and only one meaning is the rename target.** (1) the aggregate = the retro session (ADR-018 rename target); (2) `SprintState`/`SprintPhase`/`SprintAction`/`ISprintAction` = retro lifecycle types (homonyms); (3) `Participant.SprintId`/`Card.SprintId`/etc. = FK columns + the `"sprintId"` claim + `"sprint:{id}"` group + `JoinSprint` hub method (wire homonyms). A naive "replace Sprint→RetroSession" would rewrite all three and churn the SignalR/FK wire layer for zero semantic gain. Lesson: this is exactly the type-move "non-call homonym" carve-out — before scoping a rename, partition the token's occurrences by *meaning*, not by count, and make each partition a separate scope decision (Q1).

- **`SprintSynced` already exists in `Blocks.Contracts` and carries only thin fields (`SprintId/SprintName/BoardId/SyncedAt/State`) — the rich metrics are a *different* channel (gRPC `AnonymizedSprintSummary`, RA4's client).** This is what makes the RA3/RA4 split clean: RA3 = event→projection (thin), RA4 = gRPC→on-demand panel (rich). Reading both contracts up front prevented scoping RA4's gRPC client into RA3. Lesson: when two passes touch the same domain object via two channels, read *both* contract types before scoping either pass — the field gap between them is the scope boundary.

- **"Drop standalone X creation" is a premise-ambiguous directive.** The backlog's "drop standalone sprint creation" reads literally as "delete the create endpoint," but the only system-coherent reading is "creation now requires a Fokus-sprint reference" (a `RetroSession` must still be creatable; ADR-018 says it references 1..N Fokus sprints). Surfaced as Q3 rather than assumed. Lesson: a "drop/remove" directive that would leave the system unable to do something it must still do is almost always a "constrain," not a "delete" — flag it, recommend the coherent reading, but don't bake the literal reading into a plan.

- **All five judgment calls are scope/risk-tolerance decisions, not architect-adjudicable code facts — so all route `To: user`, unlike RA2 where Q3/Q4/Q5 were ADR-adjudicable.** RA2's questions resolved from ADR-016/021/022 + grep. RA3's resolve only from owner intent on sequencing (Q1 homonym depth, Q2 wire timing, Q3 creation semantics) and risk tolerance (Q4 thin-snapshot, Q5 disposable DB). The ADRs name the end-state but not the *per-pass* boundary. Lesson: the escalation test ("does answering require a preference the ADRs don't encode?") cleanly separated these from RA2's — when a question is about *which pass does what*, the ADRs rarely encode it and it's a user call.

### Phase-2 plan authoring (all 5 answers user-confirmed)

- **A confirmed answer can still leave a sub-ambiguity at the seam between two answers — resolve it deterministically in the plan, don't re-ask, but flag it.** Q1(b) keeps `SprintId` FK columns; Q2 renames HTTP routes. The collision: 24 child-resource routes use the flat `/api/sprints/{sprintId}/*` form whose `{sprintId}` param IS the kept FK column. Renaming those routes contradicts Q1(b); keeping the param while renaming the path is incoherent. This wasn't a *new* question — it follows deterministically (the flat family stays, only the 6 resource-noun lifecycle routes rename). I resolved it in-plan with a binding DO-NOT-TOUCH carve-out + a one-line "if you want the flat family renamed now, that reopens Q2" flag. Lesson: a multi-answer scope produces seam-ambiguities the individual questions didn't; the architect's job at plan time is to resolve the ones that follow deterministically from the confirmed answers (and only re-escalate the ones that don't), not to bounce every seam back to the user.

- **The load-bearing infra fact for the consumer step was "where is `AddMassTransit`" — and it's NOT in the consuming module.** The single in-memory bus lives in `Fokus.API/DependencyInjection.cs:36`; Reflekt has zero MassTransit registration. So "Reflekt consumes `SprintSynced`" is not a Follow-the-skill step — it's a Build (add a registration onto the *shared* bus without spawning a second `AddMassTransit`, a known MassTransit footgun) then Follow. Grepping `AddMassTransit` across the whole solution (1 hit, in Fokus) before writing the step turned a would-be "Follow add-integration-event" into the correct "Build then Follow" with a pre-sanctioned escalation. Lesson: for any "module X now consumes event E" step, grep the bus registration site first — if the bus isn't in module X's DI, the step has a Build half (bus topology) the skill won't cover.

- **A preserved name and a renamed name in the SAME file is the highest-risk spot for a "looks inconsistent" false-flag at review — call it out in the plan.** `SprintHub` (class name preserved, Q2) injects `SprintRepository` (renamed → `RetroSessionRepository`, Q1). I added an explicit note in the rename table so the done-check/critic doesn't flag the kept `SprintHub` as a missed rename, and doesn't flag the renamed repo resolve as a wire break. Same for `GetSprintSummary` (route kept, flat family) returning `RetroSessionSummaryResponse` (renamed). Lesson: wherever a DO-NOT-TOUCH item and a rename-target item co-occur in one file, pre-state the mix in the plan — it's exactly where a conformance reviewer (human or critic) will otherwise raise a spurious finding.

- **The acceptance greps carry exact plan-time counts, not "0 stale hits" prose (RA2's hardest lesson, applied preemptively).** Every rename/route step's acceptance pastes the *exact* grep + its expected count derived by running it now (e.g. flat routes = 24, `SprintState|SprintPhase|...` → 0 excluding Migrations/). The done-check becomes a deterministic re-run + diff, and the count is the contract. Lesson carried forward from RA2's critic-CRITICAL root cause: an acceptance grep authored from inspection rather than execution is self-inconsistent by construction — so I ran each one at plan time.

### Critic round-1 revision (code-grounded critic; REJECT → 1 CRITICAL + 1 HIGH + 1 MEDIUM + 1 LOW, all folded)

- **My route inventory was off by one because I partitioned routes by a *grep-pattern* (`/api/teams/{teamId}/sprints…` for "rename" vs `/api/sprints/{sprintId}/…` for "keep") but enumerated the rename TABLE from the files I'd opened — and `SetReviewStatusEndpoint` was a team-scoped route I never opened.** The Step-5 acceptance grep (`/api/teams/{teamId}/sprints` → 0) would actually have *caught* it at done-check — but the rename *table* (the developer's instruction list) was missing the row, so the developer would have hit an unsatisfiable acceptance mid-implementation. Lesson (sharpens the RA2 rule): "derive the file list from the exact acceptance grep" means the table rows AND the acceptance grep must come from the *same executed query* — I had the grep right but hand-curated the table from memory of opened files. Run the grep, paste its *full* hit list into the table, don't transcribe from what you read.

- **The CRITICAL wasn't the missed route — it was the FK semantics riding inside it.** `SetReviewStatusEndpoint.cs:75` passes `command.SprintId` into `Card.SetReviewStatus(reviewStatus, sprintId)` → the **kept** `Card.ReviewedInSprintId` FK column. So renaming the route's command property (`SprintId`→`RetroSessionId`, correct per Q2) sits one line away from a column the same plan says to KEEP (`SprintId`, Q1=b). A naive "rename SprintId everywhere in this file" would have renamed the domain method param and bled toward the FK. This is the exact value-space-flip-adjacent trap RA2 flagged: a rename touching a method that feeds an FK needs the FK-stays boundary stated *at the call site*, not just in a table elsewhere. Lesson: when a renamed request property is an *argument* to a method that writes a kept FK, pin "the parameter renames, the method signature + FK column do NOT" right next to the call-site line ref.

- **A 4th FK to the renamed principal was invisible to my "child FK columns" enumeration because it has a non-obvious name (`ReviewedInSprintId`, not `SprintId`).** I grepped `\bSprintId\b`-style for child FKs and found the three `SprintId` columns, but `Card.ReviewedInSprintId` (`CardConfiguration.cs:32`) is a *second* FK from `Card` to `Sprints` under a different name. Lesson (type-move rule sharpening): to enumerate ALL FKs to a renamed principal, grep the **`HasForeignKey`/`HasOne<PrincipalType>` configuration lines**, not the column-name pattern — a column whose name doesn't contain the principal's name (here `ReviewedIn…`) is exactly the one the name-pattern grep misses, and it's the one EF's principal-rename cascade can silently rename.

- **The critic caught a guardrail violation in my Build instruction that I'd left as an open A/B for the developer.** My Step-4 option (a) ("`AddConsumers(Reflekt assembly)` at the single bus site") would, if that site is `Fokus.API`, force a Fokus→Reflekt project reference — the no-cross-module-ref guardrail. I'd written the A/B without checking that option (a)'s *placement* was guardrail-legal. Lesson: when a plan offers the developer an A/B for a composition decision, each branch must itself be pre-checked against the binding guardrails — an option that violates a guardrail isn't a developer's-choice, it's a defect I should have struck (RA2 lesson "strike the rejected option from the plan, don't just over-rule it" — applied here by marking (a) REJECTED with the reason, not deleting the discussion).

- **All four fixes were completeness/consistency gaps *within* the locked Q1/Q2 scope — none reopened a user answer, so no re-escalation.** #1's "rename `SetReviewStatus` now" is consistent with Q2 ("rename team-scoped routes freely") and the user explicitly directed it; #2/#3/#4 are pure groundedness fixes. Re-grounded steps 4/5/6 against code per the revision rule before folding. Lesson: a critic REJECT on a well-scoped plan is usually *enumeration* gaps (missed routes/FKs/guardrail checks), not *decision* errors — fix in-place and auto-approve; only re-escalate if a finding contradicts a confirmed answer.

### Step-1 done check (independent code-grounded verification)

- **The grep-table acceptances + the pasted exact counts converted the done-check into a deterministic re-run — and that's where the verification paid off.** Re-running `/api/teams/{teamId}/sprints`→0, `/api/teams/{teamId}/retro-sessions`→9, `/api/sprints/{sprintId}`→26, `SprintState|SprintPhase|…`→0 took four greps with pre-stated expected results; every one matched. The two seams (migration FK-cascade, single-bus) needed reading actual code (`Up()`, the three DIs) — not greppable — but the *rename* conformance was a pure diff. Lesson reinforced from RA2: a rename/route step whose acceptance is a pasted grep+count makes the done-check fast AND trustworthy; the only slow part is the genuinely code-shaped seams.

- **My plan-time flat-route count (24) was wrong — the true baseline is 26 — and the developer caught it.** I undercounted the `/api/sprints/{sprintId}` family at plan time (missed 2: `GetMyVotes`, `GetParticipants`/`GetCurrentParticipant`-class routes). The developer recorded "26 not 24" and used 26 in the acceptance. This did NOT cause a conformance failure (the flat family was fully preserved, which is the binding requirement), but my cited count was off. Lesson: even a "run the grep at plan time" count can be wrong if the grep pattern isn't the *exact* one the acceptance will use — I globbed `/sprints/{sprintId}` loosely at plan time vs the precise literal. When a count is a binding acceptance number, paste the literal grep AND its output, not a hand-counted total; a developer re-running the precise query is the backstop that caught my 24.

- **A "Deviated (valid reason)" is the right disposition for the dropped `Cards` FK constraints — but the substantive judgment is the reviewer's, not mine.** The migration preserved all four FK *columns* (the binding Q1=b/HIGH#2 requirement — verified byte-identical) but dropped two `Cards` FK *constraints* without re-adding them. That's a real behavioral change (loss of DB-enforced cascade/set-null on `Cards`), reason documented, build+migration clean → done-check PASS as Deviated. But I explicitly flagged it as the one item for the reviewer to adjudicate (model-vs-snapshot drift risk: EF still declares the `HasOne<RetroSession>()` so a future `migrations add` would try to re-add them). Lesson: the done-check's job is "is the step done + reason valid," not "is the deviation's design correct" — disposition it Deviated, verify the binding invariant held (columns preserved), and route the design judgment to Step 2 rather than absorbing or Failing it.

- **Pre-commitment predictions landed on the exact three seams the prompt flagged, and all three held — convergence is the signal.** I predicted (route incompleteness, FK cascade, second bus) before reading impl; the prompt named the same two seams; all came back clean. When the risk-ranked predictions, the prompt's named checks, and the result all converge clean, that triangulation is stronger evidence than any single grep. Lesson (reinforced from RA2): risk-rank the likely gaps before reading the implementation, then a clean pass on the *predicted* failure points is the confidence — not a clean pass on a flat checklist.

## Developer Lessons

- **`MassTransit.Testing` is not a real package (v9); the test harness types ship in `MassTransit.TestFramework`.** The NuGet package named `MassTransit.Testing` does not exist in the v9.x feed — adding it causes a NU1100 not-found error. The correct package is `MassTransit.TestFramework` (same version pin as `MassTransit`). When bootstrapping test projects that use `ITestHarness`/`AddMassTransitTestHarness`, always use `MassTransit.TestFramework`, not `MassTransit.Testing`.

- **SQLite :memory: isolation — shared connection is mandatory when consumer DI scope and test assertion scope must see the same rows.** Each call to `new SqliteConnection("Data Source=:memory:")` creates a separate, isolated in-memory DB. If a MassTransit consumer resolves a `DbContext` from a scoped DI scope (separate from the test's scope), the two contexts are on different connections and neither sees the other's rows. Fix: create one `SqliteConnection` in the test constructor, open it, and pass it to all `AddDbContext` calls. EF Core holds a reference but does not open/close the connection if you pass a pre-opened one.

- **`add-integration-event` skill confirmed publisher-oriented only.** The skill's Consumer.md covers "create a consumer in target service" but says nothing about the shared-bus registration topology (moving `AddMassTransit` from one module to Host). The Step-4 Build instruction in the plan was necessary precisely because the skill doesn't cover it. The gap is confirmed — the plan's escalation seam was the correct mitigation for this pass.

- **`MassTransit.TestFramework.AddMassTransitTestHarness` + shared SqliteConnection = correct pattern for EF Core integration tests with in-memory transport.** Use `services.AddMassTransitTestHarness(cfg => cfg.AddConsumer<TConsumer>())` instead of `services.AddMassTransit(...)` in tests. The test harness wires in-memory transport automatically; you only need to `await _harness.Start()` and `await _harness.Bus.Publish(...)`. Assertion: `await _harness.Consumed.Any<TEvent>(ct)` waits for the consumer to finish before you query the DB.

- **Central Package Management enforces version centralization strictly (NU1010).** Adding a `<PackageReference>` in a `.csproj` without a matching `<PackageVersion>` entry in `Directory.Packages.props` causes `error NU1010: ... missing from the central package management file`. Always add the version entry to `Directory.Packages.props` first, then add the bare `<PackageReference>` in the project. Do not guess the version; check what sibling projects already pin for the same package family.

## Reviewer Lessons

- **A `\r\n` literal embedded in a `//` comment makes a fluent-builder call look like active code.** When reviewing EF configuration files, `grep -n "HasOne"` on the raw file is necessary — the Read tool renders `\r\n` as actual line breaks in its display, making commented-out calls appear as separate active lines. The tell is: if `dotnet ef migrations has-pending-model-changes` reports "No changes" but the configuration appears to declare a relationship, suspect the builder call is inside a comment and grep the raw file to confirm.

- **Model-vs-snapshot drift adjudication requires running `has-pending-model-changes`, not just reading the snapshot.** The architect's note ("EF still declares HasOne<RetroSession>() for both Cards FKs — a possible model-vs-snapshot drift") was correct in identifying the risk, but resolving it required running the CLI command. A visual snapshot comparison against the configuration file without running the EF tool can produce false positives (as here: the snapshot appeared inconsistent until the tool confirmed no pending changes, revealing the builder calls were commented out).

- **When a migration drops FKs and does not re-add them, always grep `CardConfiguration` (or the equivalent configuration file) for the matching `HasOne` calls and verify they are active code, not dead code.** Dead-code `HasOne` calls in EF configuration are silently ignored by EF but create a misleading picture for readers. This pattern is a maintenance trap for future passes (RA5 in this case).

- **Delta-only re-scaffold is the correct pattern when the original migration was already applied to a DB and only a model-gap needs adding.** When a configuration fix re-activates previously dead-code `HasOne<T>()` calls, delete the original unapplied (or throwaway-applied) migration and re-scaffold. EF scaffolds only the model-gap additions as a delta `Up()`, not the full schema again. `has-pending-model-changes` cleanly confirms "No changes" afterward when the snapshot and model agree.
