# Reflekt v1 — Specification

**Status:** Complete (shipped)
**Owner:** Laurentiu

---

## 1. Purpose & Scope

Reflekt is an open-source sprint retrospective tool for .NET teams. V1 is the feature set that runs a real retro: write cards, group related observations, vote on what matters, discuss top themes with structured facilitation, capture action items, and generate a report.

**What V1 is:**
- A web app where a team runs a retro: write cards, group them, vote, discuss with facilitator-driven focus, capture action items, generate a report.
- Anonymous participation via a shared room link. No participant accounts.
- Strictly enforced retro phases — every action is gated by the current phase via an action matrix.
- First-class evidence linking on cards (GitHub PRs/commits, Jira issues, generic URLs with OpenGraph previews).
- Real-time collaborative UI over SignalR.

**What V1 is NOT (by design, not oversight):**
- A memory layer, agent-authored cards, or the Feedback Flywheel loop — those are v2+.
- A Parabol/EasyRetro replacement. V1 shipped for Laurentiu's team first and doubles as course material for the Claude Code for .NET course (June 2026).
- A product. It's a feature used internally. Productization is a later decision gated on real usage signals.

## 2. Non-negotiables

- **.NET 10 + Vue 3 stack.** Matches Laurentiu's expertise and the course narrative. Authoritative technical architecture lives in `docs/architecture/reflekt/v1.md`; this spec defers to it for anything not a business decision.
- **Schema decisions must be forward-compatible with v2 (memory layer + agents).** Specifically: `Card.CardType` enum must accommodate `AgentAuthored` later; card/vote ownership must attribute to a `Participant`, not a freeform string.
- **Practical over complete.** Build features, not a product. If a feature doesn't earn its hours, cut it.

## 3. Identity & Authentication

Reflekt has two identity tiers. Don't blur them.

### 3.1 Team creator — Google-authenticated

- A **Team** is created by a Google-authed user (the Scrum Master, initially Laurentiu).
- Google OAuth 2.0 — email + profile name + given name. No photo, no extended scopes.
- The team creator is also the **Scrum Master** for all sprints under that team. Roles are not split in v1.
- **Sprint creation is gated to the team creator.** Other Google-authed users cannot create sprints under someone else's team in v1. No invite flow, no multi-admin.

**Why:** V1 serves one team. Team invite flows, role hierarchies, and multi-admin are real features but not essential for v1. Defer to v2.

### 3.2 Sprint participants — ephemeral guests

- Participants enter a sprint via a shareable **room link**: `/sprint/{sprintId}`.
- On first visit, participant picks a display name. That's the entire onboarding.
- No accounts, no email, no password.
- A `guestToken` (GUID) is generated **server-side** on first join and returned to the client. It is stored in `localStorage` under a sprint-scoped key: `reflekt:sprint:{sprintId}:token`.
- On every API call and SignalR connection, the token is sent as a header.
- Backend matches token -> `Participant` row. If no match, create a new `Participant` and return the token.
- **Silent rejoin on refresh.** If a matching token is found in localStorage on page load, rejoin as the existing participant without prompting. No "Welcome back, Ana" dialog.
- Switching devices mid-retro = new participant, pick name again. Acceptable tradeoff.
- **Display name uniqueness:** Display names must be unique within a sprint (case-insensitive comparison). If a duplicate name is submitted, the join endpoint returns 409 with "Name already taken."
- **Name-picker shows existing participants.** Later joiners see the list of already-joined participants above the name input, so they know what names are taken before submitting.

**Why this model (not pure anonymous, not full accounts):**
- Pure anonymous breaks "edit your own cards" — participants can't prove ownership after refresh.
- Full accounts add friction the team doesn't need.
- localStorage guest token gives real ownership semantics and dies cleanly with the session.
- Server-generated tokens prevent client-side forgery and GUID collision with no added complexity.

### 3.3 Ownership semantics

- Every `Card` and `Vote` references a `ParticipantId`.
- Edit a card: requires `card.ParticipantId == request.ParticipantId` **OR** caller is the Scrum Master.
- Delete a card: requires caller is the **Scrum Master**, OR `card.ParticipantId == request.ParticipantId` (own cards only).
- The Scrum Master can do anything. Participants can only act on their own cards.
- **Kick participant:** The Scrum Master can kick a participant from the sprint management page. Kicked participants are removed, their guest token is revoked, their SignalR connection is closed, and `ParticipantLeft` is broadcast to the remaining clients.

### 3.4 Creator auto-join

When the sprint creator (SM) opens the retro room, they are auto-joined as a participant using their Google `given_name` — no name-picker shown. The flow is frontend-orchestrated: the frontend detects no guest token in localStorage, confirms the user is signed in, fetches `given_name` from `GET /auth/me`, and calls the standard `POST /api/sprints/{sprintId}/join` automatically.

- If auto-join succeeds (201), the SM enters the room immediately.
- If the name is already taken (409), the SM falls through to the name-picker with an error pre-populated.
- If a valid guest token already exists in localStorage, the normal silent-rejoin flow runs instead — auto-join is not attempted.

See `<reflekt-repo>/docs/features/CreatorAutoJoin.md` (the original Reflekt project) for the full flow and API surface changes.

## 4. Core Entities

Minimal schema. Extend as needed but don't invent fields we don't use.

> **ID convention:** All entity IDs are **auto-increment integers** (`int`), not GUIDs. Foreign keys follow the same type.

```
Team {
  Id: int                      // auto-increment
  Name: string
  CreatorEmail: string        // Google-authed user
  CreatedAt: DateTime
}

Sprint {
  Id: int                      // auto-increment
  TeamId: int
  Name: string                // e.g. "Sprint 47"
  State: enum { Draft, Active, Closed }
  CurrentPhase: enum { Writing, Grouping, Voting, Discussing, Reporting }
  VotesPerParticipant: int    // default 3, set at creation
  CreatedAt: DateTime
  ClosedAt: DateTime?
}

Participant {
  Id: int                      // auto-increment
  SprintId: int
  DisplayName: string         // unique within sprint, case-insensitive
  GuestToken: string           // GUID string, generated server-side on join
  JoinedAt: DateTime
}

CardGroup {
  Id: int                      // auto-increment
  SprintId: int
  ColumnType: enum { WentWell, DidntGoWell }  // never ActionItems
  Title: string?               // facilitator-assigned theme label, max 100 chars
  DiscussedAt: DateTime?       // set when marked as discussed during Discussing phase
  CreatedAt: DateTime
}

Card {
  Id: int                      // auto-increment
  SprintId: int
  ParticipantId: int           // author
  GroupId: int?                // FK to CardGroup; null during Writing, set from Grouping onward for Notes; always null for ActionItems
  ColumnType: enum { WentWell, DidntGoWell, ActionItems }
  CardType: enum { Note, ActionItem }
  Text: string
  AssigneeName: string?        // nullable; only set when CardType == ActionItem
  CreatedAt: DateTime
  UpdatedAt: DateTime
}

Vote {
  Id: int                      // auto-increment
  GroupId: int                 // FK to CardGroup — votes target groups, not individual cards
  ParticipantId: int
  CreatedAt: DateTime
}
// Note: Vote is a value object owned by the CardGroup aggregate,
// not a separate aggregate root. Votes have no independent lifecycle outside their group.

EvidenceLink {
  Id: int                      // auto-increment
  CardId: int
  Url: string
  Source: enum { GitHub, Jira, Generic }
  Title: string?
  Description: string?
  IconUrl: string?
  ImageUrl: string?
  ExternalKey: string?         // e.g. "PROJ-123" for Jira, nullable otherwise
  FetchedAt: DateTime?
  FetchStatus: enum { Pending, Ok, Failed }
}
```

**Notes:**
- `AssigneeName` is a **string copy**, not a foreign key. Action items outlive their assignee participant (who dies with the sprint), and we read the name off the card at retro time. No cross-sprint linking needed.
- `Vote` targets a `CardGroup`, not a `Card`. Since every Note card belongs to a group from the Grouping phase onward (solo groups for ungrouped cards), all voting happens at the group level.
- `CardGroup` is auto-created at the Writing -> Grouping phase transition (one solo group per Note card) and manually created by the SM during Grouping.
- `CardGroup.DiscussedAt` is set during Discussing when the SM marks a group as discussed — either manually or automatically when focus moves to another group.
- Vote-per-card-type constraint (no voting on ActionItem groups) is enforced in the **API layer**, not the schema. Keeps schema simple.
- All foreign keys cascade-delete on `Sprint` removal (not that we delete sprints in v1, but set it up now).

## 5. Retro Mechanics

### 5.1 Columns

**Fixed three-column layout, hardcoded in v1:**
1. **Went well** — `ColumnType.WentWell`
2. **Didn't go well** — `ColumnType.DidntGoWell`
3. **Action items** — `ColumnType.ActionItems`

**Why this template specifically:**
- The third column is already the action-items column, matching the v2 "action items -> PRs against CLAUDE.md" pattern. No special casing needed later.
- Not user-configurable in v1. Zero UI cost.

### 5.2 Phases

Sprint has a `CurrentPhase`: `Writing -> Grouping -> Voting -> Discussing -> Reporting`.

- Scrum Master advances the phase manually with a button.
- **Phases are strictly enforced via an action matrix.** Every sprint mutation is gated by the current phase. Actions not permitted in the current phase are rejected by the backend (409) and hidden or disabled by the frontend.
- The permitted (phase, action) pairs are seeded product data exposed via `GET /api/phase-actions`. Both the backend and frontend read from this single source of truth. See `<reflekt-repo>/docs/features/PhaseActionGating.md` for the full matrix and enforcement details.
- `Reporting` is the terminal phase — it permits no actions. The SM then closes the sprint separately (state transition), which is independent of phase.
- **Advance gate (Discussing -> Reporting):** At least 2 groups must be marked as discussed before the SM can advance. The backend enforces this with 409. The frontend shows a confirmation dialog with the count before advancing.

**Note on naming:** The sprint has two independent machines — a state machine (`Draft -> Active -> Closed`) and a phase machine (`Writing -> Grouping -> Voting -> Discussing -> Reporting`). The terminal phase is `Reporting`, not `Closed`, to avoid ambiguity with the sprint state value `Closed`.

**Action matrix:**

| Action | Writing | Grouping | Voting | Discussing | Reporting |
|--------|---------|----------|--------|------------|-----------|
| CreateNote | yes | | | | |
| EditNote | yes | | | | |
| DeleteNote | yes | | | | |
| GroupCards | | yes | | | |
| UngroupCards | | yes | | | |
| RenameGroup | | yes | | | |
| CastVote | | | yes | | |
| RetractVote | | | yes | | |
| CreateActionItem | | | | yes (SM) | |
| EditActionItem | | | | yes (SM) | |
| DeleteActionItem | | | | yes (SM) | |
| AttachEvidenceLink | yes | | | yes | |
| DetachEvidenceLink | yes | | | yes | |
| FocusGroup | | | | yes | |
| ToggleDiscussed | | | | yes | |
| AdvancePhase | yes | yes | yes | yes | |

### 5.3 Card Grouping

During retros, teams surface duplicate or related observations. Card grouping clusters related notes into a single votable and discussable unit during a dedicated **Grouping** phase between Writing and Voting.

- **Auto-creation:** When phase advances from Writing to Grouping, the system creates a solo `CardGroup` for every Note card. Every Note card belongs to exactly one group from this point forward.
- **Facilitator-driven:** During Grouping, the SM merges related cards into groups, removes cards from groups, dissolves groups, and assigns theme titles (e.g., "CI/CD issues", "Team morale"). Participants see groups update in real-time but cannot modify them.
- **Groups persist** through Voting, Discussing, and Reporting. They are not dissolved after Grouping ends.
- **Same-column only.** Cards can only be grouped within the same column. A WentWell card cannot join a DidntGoWell group. Action items are never grouped.
- **Display label:** A group's label is its title (if set by the SM) or the earliest card's text (by creation time).
- **Solo groups** (one card, no explicit title) are visually indistinguishable from ungrouped cards — the grouping is transparent to the user.

See `<reflekt-repo>/docs/features/CardGrouping.md` for the full entity definition, API surface, and business rules.

### 5.4 Voting

- **Dot voting on groups.** Each participant gets `Sprint.VotesPerParticipant` votes (default 3, configurable at sprint creation).
- Participant can spend votes however they want — all on one group, spread across groups, abstain.
- Real-time: vote counts visible to everyone as they're cast.
- **Anonymous:** groups show count, not who voted.
- **Votes target groups, not individual cards.** Since every Note card belongs to a group (solo or merged) from the Grouping phase onward, all voting happens at the group level. Solo groups are votable just like multi-card groups.
- A participant may place **multiple votes on the same group** (budget permitting) — there is no one-vote-per-group limit.
- Retracting removes **one vote at a time** from the group, not all of a participant's votes on it. Repeat retract to remove additional votes.
- **No voting on action items.** Action items are never grouped and have no vote mechanism.

### 5.5 Discussion Flow

The Discussing phase has a structured facilitation flow controlled by the SM.

- **Discussion focus:** The SM clicks "Discuss" on a group to highlight it for all participants via SignalR. At most one group can be focused at a time.
- **Auto-marking:** When focus moves from one group to another, the previously focused group is automatically marked as "discussed." The SM can also toggle the discussed state manually.
- **SM-only action items:** Only the SM can create, edit, or delete action items during the Discussing phase. Participants see the action items list as read-only.
- **Focus survives reconnection.** A participant who refreshes during Discussion sees which group is currently focused.
- **Advance to Reporting:** When the SM advances, the currently focused group (if any) is auto-marked as discussed before the phase transition occurs.

See `<reflekt-repo>/docs/features/DiscussionFlowAndReporting.md` for the full flow, API surface, and SignalR events.

### 5.6 Card editing & deletion

- **Edit:** card author OR Scrum Master.
- **Delete:** card author OR Scrum Master.
- Last-write-wins on the rare concurrent-edit case (author + Scrum Master editing simultaneously). No locks, no merge UI.
- If a card is deleted while someone is editing it, their save fails with a toast: "Card was removed."

### 5.7 Card & group ordering

- **Writing phase:** newest cards first (natural for "I just thought of something").
- **Grouping phase:** cards displayed within their groups; groups sorted by earliest card creation time.
- **Voting / Discussing phase:** groups sorted by vote count descending within each column. Discussion flows top-down through highest-voted groups.
- **Reporting phase:** same as Voting/Discussing.

## 6. Evidence Links

The differentiating feature of Reflekt vs Parabol/EasyRetro. Cards can carry Jira / GitHub / generic URL previews.

### 6.1 Supported sources

Auto-detected by URL pattern on paste:

| Source | Detection | Data we fetch |
|---|---|---|
| **GitHub** | `github.com` host | OpenGraph: title, description, image, icon |
| **Jira** | Host matches configured Jira domain, OR URL matches `*/browse/{KEY}` pattern | **Issue key only**, extracted from URL. No API call. |
| **Generic** | Anything else | OpenGraph fallback: title, description, image, icon |

### 6.2 Fetching behavior

- **Async, non-blocking.** On paste: save `EvidenceLink` with `FetchStatus = Pending`, show bare URL immediately, kick off background fetch, push enriched metadata via SignalR when ready.
- **Never block the UI on a fetch.** A slow OpenGraph fetch should not delay card creation.
- **Failure mode:** if fetch fails, set `FetchStatus = Failed`, display bare URL with domain favicon. Don't retry automatically.
- **Jira links skip fetching.** The issue key is extracted from the URL and FetchStatus is set to Ok immediately — no HTTP request needed.

### 6.3 Implementation

- **Server-side fetch** using `HttpClient` + `AngleSharp` for HTML parsing. **Do not pull a dedicated OpenGraph library.**
- `BackgroundService` + `Channel<FetchJob>` for async processing.
- Timeout: 5 seconds per fetch.
- **SSRF safety:** reject requests to localhost, private IP ranges (10.x, 192.168.x, 172.16.x), and non-HTTP(S) schemes. Basic hostname validation is sufficient — this is for internal team use, not hostile multi-tenant.

### 6.4 Display

- **Inline mode only in v1.** Compact rendering: favicon + title + (for Jira) issue key chip.
- Card mode (full preview box with description and image) is a future nice-to-have.
- Clicking a preview opens the URL in a new tab.

## 7. Real-time (SignalR)

### 7.1 Events pushed to all clients in a sprint

| Event | Payload |
|---|---|
| `CardCreated` | Full card object |
| `CardUpdated` | Full card object |
| `CardDeleted` | Card ID |
| `VoteCast` | `{ groupId, newCount }` |
| `VoteRetracted` | `{ groupId, newCount }` |
| `PhaseChanged` | New phase enum value |
| `ParticipantJoined` | Participant object (id, name) |
| `ParticipantLeft` | Participant ID |
| `EvidenceLinkFetched` | Full `EvidenceLink` object with metadata |
| `GroupCreated` | `{ group: { id, sprintId, columnType, title, cardIds } }` |
| `CardsGrouped` | `{ groupId, cardId, sourceGroupId }` |
| `CardUngrouped` | `{ cardId, newGroupId, sourceGroupId }` |
| `GroupDissolved` | `{ groupId, newGroups: [{ id, cardIds }] }` |
| `GroupTitleChanged` | `{ groupId, title }` |
| `GroupFocused` | `{ groupId, previousGroupId?, previousGroupDiscussed? }` |
| `GroupFocusCleared` | `{ previousGroupId?, previousGroupDiscussed? }` |
| `GroupDiscussedChanged` | `{ groupId, isDiscussed, discussedAt? }` |

### 7.2 Not pushed

- **Card draft text while typing.** Too chatty, no value — retros want finished thoughts, not live typing. Only push on save.

### 7.3 UI behavior

- **Optimistic.** Local action (create, edit, vote) updates the UI immediately, then fires the API call.
- **On API success:** reconcile if the server response differs from the optimistic assumption. Rare.
- **On API failure:** revert the optimistic update, show a toast: "Couldn't save — reconnecting..."

### 7.4 Connection loss & reconnect

- SignalR auto-reconnect is enabled (built-in).
- On reconnect, the client **refetches the full sprint state** (cards, groups, votes, phase, participants, focus state). Cheap for a 50-card retro.
- No offline queue, no local-first sync. Overkill for v1.

## 8. Action Items

Action items are cards in the third column with a distinct `CardType` and an assignee.

- `CardType = ActionItem`, `ColumnType = ActionItems`.
- `AssigneeName` is a **string** (the display name of a participant at assignment time), copied onto the card. Not a foreign key — captures the commitment even if the assignee doesn't rejoin future sprints.
- Assignee is chosen from a dropdown of current participants in the sprint when the action item is created or edited.
- **SM-only in Discussing phase.** Only the Scrum Master can create, edit, or delete action items during the Discussing phase. Participants see the action items list as read-only. See `<reflekt-repo>/docs/features/DiscussionFlowAndReporting.md`.
- **No voting on action items.** Action items are never grouped and have no vote mechanism.
- Action items **can have evidence links** (e.g., "update deployment doc" -> link to the doc or relevant PR).

## 9. Sprint Lifecycle

```
Draft --(SM starts sprint)--> Active --(SM closes sprint)--> Closed
```

- **Draft:** Sprint exists, room link not yet shared with team. Optional state — SM may create-and-start in one action.
- **Active:** Room link is live. Participants can join, write cards, vote, etc.
- **Closed:** Read-only. No new cards, no edits, no votes, no phase changes. Report is accessible. Closed sprints stay in the team's sprint list — no archive concept.

**Why closed = strictly read-only:** Matches the "compute report on demand" decision (SS10). If closed sprints were editable, the report could drift from the version the team reviewed at close. Making closed sprints immutable means we never need snapshot logic.

SM transitions states manually. No auto-close on phase reaching `Reporting`; the phase and the sprint state are independent concepts.

## 10. Report

### 10.1 Endpoints

**SM-facing (team-scoped):**
```
GET /api/teams/{teamId}/sprints/{sprintId}/report
```

**Participant-facing (sprint-scoped):**
```
GET /api/sprints/{sprintId}/report
```

Both return the same JSON. The participant-scoped endpoint does not require the team ID, making it accessible from within the retro room where participants only know the sprint ID.

### 10.2 Content

```json
{
  "sprint": { "id", "name", "createdAt", "closedAt" },
  "team": { "id", "name" },
  "participants": [ { "displayName" } ],
  "notes": {
    "wentWell": [
      {
        "groupTitle": "...",
        "isDiscussed": true,
        "voteCount": 5,
        "cards": [
          { "text": "...", "evidenceLinks": [...] }
        ]
      }
    ],
    "didntGoWell": [ /* same structure */ ]
  },
  "actionItems": [
    { "text", "assigneeName", "evidenceLinks": [...] }
  ]
}
```

- **Notes:** Groups where **discussed = true OR voteCount > 1**, sorted by vote count descending. Groups with exactly 1 vote that were not discussed are excluded — self-voting inflates >=1 counts to most cards, making that threshold meaningless. The discussed flag captures what the team actually talked about; the >1 vote threshold captures topics with genuine interest beyond the author. Each group shows a "Discussed" indicator.
- **Action items:** all of them, regardless of votes.
- **Evidence links:** embedded on their parent cards.
- **Solo groups** (one card, no explicit title) render identically to how individual cards would — the grouping is transparent.

**What's NOT in the report:**
- Card author names (anonymous model).
- Card timestamps.

### 10.3 Reporting phase experience

In the Reporting phase, the report is rendered inside the retro room for **all participants** — not behind a separate route that only the SM knows about. Participants can toggle between:

- **Report view (default):** Structured report with discussed/voted groups, action items, and "Copy as markdown." Each group shows a "Discussed" badge if it was discussed.
- **Board view:** Read-only version of the board as it appeared at the end of Discussion. All groups, cards, vote counts, and discussed marks visible. No forms, no mutation controls.

Both SM and participants see the same views. There is no SM-exclusive view in Reporting.

### 10.4 Storage policy

- **Computed on demand, not stored.** No `Report` entity.
- Endpoint is a read view over sprint data with filtering + sorting.
- Closed sprints are read-only (SS9), so there's no drift risk.

**Why compute-on-demand over snapshot:**
- Compute cost is trivial — one SQL query with joins, sub-10ms for 50-card retros.
- Snapshotting creates two sources of truth and invalidation logic we don't need.

### 10.5 Export

- **"Copy as markdown"** button on the report page, available to all participants. Serializes the report to markdown in the clipboard, including the discussed/undiscussed distinction per group.
- Solves the paste-into-Confluence / paste-into-Slack workflow that every retro-tool user complains about.
- **No PDF export** in v1 (requires a library + layout work, wrong ROI).
- **No CSV export** in v1 (wrong shape for qualitative data).
- **No Jira/Slack push** in v1.

## 11. Out of Scope (v1)

### By design — intentional product decisions

These are architectural choices, not gaps. They define what Reflekt is.

- **Author attribution on cards** — cards are anonymous. The author's `ParticipantId` is stored for ownership enforcement but never displayed to other participants.
- **Draft text real-time sync while typing** — too chatty, no value. Retros want finished thoughts, not live typing. Only push on save.
- **Participant-driven grouping** — only the SM groups cards. No "suggest a group" or collaborative grouping.
- **Cross-column grouping** — cards can only be grouped within the same column. A WentWell card cannot join a DidntGoWell group.
- **Re-grouping after Voting** — groups are frozen once Voting begins. Prevents vote manipulation.
- **Per-team or per-sprint custom phase rules** — the action matrix is a global product rule. Not runtime-tunable.
- **Auto-advance on timer expiry** — the SM decides when to move on. No automatic phase transitions.
- **Display name editing after join** — name is set once. Changing requires creating a new participant.

### Deferred — candidates for future versions

Explicitly cut from v1. These are real features worth considering for v2+.

- Column configuration UI (configurable reflection columns + fixed Action Items column)
- Phase revert / undo accidental phase advance (backlog #22)
- Open actions from previous retro (review last sprint's action items at the start of a new retro)
- Per-phase timer (countdown timer controlled by the SM, visible to all)
- Inline phase controls (move phase advance button into the retro room top bar)
- Google auth for participants (dual-path: Google sign-in or guest join)
- Multi-team support (multiple teams per Google-authed user)
- Team deletion with cascade
- Memory layer / cross-sprint queries
- Agent-authored cards
- CLAUDE.md PR generation from action items
- Jira REST API integration (beyond URL parsing + issue key extraction)
- GitHub REST API integration (OpenGraph scrape only in v1)
- Team invite flow / multi-admin / role hierarchy
- Sprint templates / clone-from-previous
- Card export to Jira/Linear as tickets
- PDF / CSV / Slack export
- Mobile-optimized UI (desktop-first; phones functional but unpolished)
- Email notifications
- Cross-sprint search
- Analytics, charts, trend dashboards
- Card preview "Card" and "Embed" display modes (inline only in v1)
- Per-group discussion timer / timebox enforcement
- Participant-driven discussion requests (SM controls discussion flow)
- AI-generated summaries of discussed groups
- ROTI / satisfaction rating at end of retro
- Skipping the Grouping phase (phase always exists; SM can advance through it immediately)
- Group templates or AI-powered auto-grouping suggestions
- Online/offline presence indicators

   _Resolved: Configuration-driven allowlist in `appsettings.json`._

7. **Seed data.**
   _Resolved: `DbInitializer` seeds dev data on startup when the database is empty._
