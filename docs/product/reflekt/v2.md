# Reflekt v2 — Specification

**Status:** Draft (corrected from PO review against v1 reality)
**Owner:** Laurentiu
**Depends on:** Reflekt v1 deployed and functional
**Related:** `docs/specs/v1.md`, `docs/backlog.md`

---

## 1. Purpose & Scope

V2 makes Reflekt usable beyond a single-team setup and fills UX gaps exposed by real usage. All features are non-AI — agent-authored cards, memory layer, Jira API integration, and cross-sprint analytics are explicitly deferred to v3.

**V2 is NOT:**
- AI-powered anything. No agent cards, no memory layer, no semantic search.
- A product launch. Still internal tooling + course material.
- A rewrite. V2 builds on v1's data model, extends it.

---

## 2. Non-negotiables

- **Proper foundations, not workarounds.** V1 stored SM identity as a plain email string on Team. V2 introduces a `User` entity and foreign key relationships. All downstream features build on this, not around it.
- **V1 is reality.** Phase sequence is `Writing -> Grouping -> Voting -> Discussing -> Reporting` (5 phases). Sprint states are `Draft -> Active -> Closed` (independent machine). These are not negotiable — v2 extends them, doesn't redefine them.
- **Design for general use.** Not limited to one team or a small group. Features should work for teams of any reasonable size (3-15+ people).

## 4. Feature Specifications

### 4.0 User Entity & Team Ownership Migration

**Problem:** V1 has no `User` entity. SM identity is a plain `CreatorEmail` string on Team, compared against Google claims at every endpoint. This is a workaround that blocks multi-team support (can't count teams per user via FK) and participant identity (no entity to link participants to).

**Decision:** Create a proper `User` entity. Migrate Team ownership from `CreatorEmail` string to a `CreatedByUserId` foreign key. Update all SM authorization checks to use the relationship.

**Data model:**

```
User {
  Id: int
  Email: string             // from Google profile, unique
  Name: string              // from Google profile
  GivenName: string         // from Google profile (used for creator auto-join)
  CreatedAt: DateTime
}
```

- `Team.CreatorEmail` is replaced by `Team.CreatedByUserId` FK to `User`.
- A `User` row is created on first Google sign-in (upserted by email).
- All SM authorization checks migrate from string comparison against `CreatorEmail` to FK-based lookup via `CreatedByUserId`.

**Migration notes:**
- Data migration: for each existing Team, create a User row from the `CreatorEmail` value, then set `CreatedByUserId` to that User's Id.
- The unique index on `Team.CreatorEmail` is dropped — it's replaced by non-unique `CreatedByUserId` (one user can own multiple teams, see §4.1).

---

### 4.1 Multi-Team Support

**Problem:** V1 enforces one team per email (unique index + existence check on creation). Users managing multiple sub-teams can't create separate retro spaces.

**Decision:** Up to 10 teams per user. The limit is a soft guard against abuse, not a technical constraint. Configurable per environment.

**Rules:**
- Any Google-authed user can create a team. They become the SM for that team.
- One user can create up to 10 teams (configurable).
- Team names must be unique per user (not globally).
- The SM dashboard (post-login landing page) shows all teams the user owns, with sprint counts and last-activity timestamps.

**Data model impact:** No new tables. The creation guard changes from "team exists for this user" to "team count < limit for this user." The unique index on the old `CreatorEmail` was already dropped in §4.0.

**UX flow:**
- After Google login, SM sees a team list (cards or table). Each team shows: name, number of sprints, last sprint date.
- "Create Team" button, gated to the configured limit.
- Clicking a team navigates to its sprint list.

---

### 4.2 Team Deletion with Cascade

**Problem:** If users can create multiple teams, they need to be able to delete teams to recycle slots. Deletion must be clean — no orphaned sprints, participants, cards, votes, or evidence links.

**Decision:** Hard delete with full cascade. No soft delete — this is a lightweight tool, not an enterprise audit trail.

**Cascade order:** Team -> Sprints -> Participants, CardGroups -> Cards -> Votes, EvidenceLinks. All in a single transaction.

**UX flow:**
- Team card/row in the SM dashboard has a delete action.
- Confirmation dialog: "Delete team '{name}' and all its sprints? This cannot be undone."
- Must type the team name to confirm (prevents accidental clicks).
- Only the team owner (SM) can delete their own teams.

**Guardrail:** Cannot delete a team that has a sprint in Active state. Draft sprints are cascade-deleted without requiring closure first (they contain no meaningful data). Close or delete active sprints first. This prevents deleting a team mid-retro while participants are connected.

---

### 4.3 Google Auth for Participants (Dual Path)

**Problem:** V1 participants are ephemeral guests — localStorage token, display name only. They can't be recognized across sprints or devices. Clearing the browser loses the session.

**Decision:** Support both Google sign-in and guest join for participants. Participants are invited via a sprint link — they choose how to identify themselves. Neither path is privileged over the other for the retro experience itself.

**Two participant identity tiers:**

- **Google-authed participant:** Signs in with Google before joining a sprint. Gets a `User` record (same entity the SM uses). Recognized across sprints, across devices, across teams. Display name pulled from Google profile.
- **Guest participant:** Same as v1. Picks a display name, gets a localStorage token, sprint-scoped. No persistence beyond the browser session.

**Data model impact:**

- `Participant` table gains an optional `UserId` FK to `User`. Null for guests, populated for Google-authed participants.
- A Google-authed user joining a sprint creates a `Participant` row linked to their `User` record.
- If they join the same sprint from another device, they rejoin as the same participant (matched by `UserId` + `SprintId`), unlike guests who would get a new participant row.

**UX flow:**

1. Participant opens the sprint link.
2. Join page shows two options: "Join with Google" (button) or "Join as Guest" (name input + join button).
3. Google path: OAuth flow -> redirected back to sprint -> auto-joined with Google profile name.
4. Guest path: enter display name -> join -> same as v1.

**Why both paths:** Not everyone has a Google account. OAuth redirects mid-meeting are friction. The guest path is the low-friction entry; Google is the upgrade path for persistent identity. Both are valid for an invitee.

**What this enables for v3:** Cross-sprint history per user, action item ownership that persists, user-level analytics.

### 4.4 Configurable Reflection Columns

**Problem:** V1 has three hardcoded columns: Went Well / Didn't Go Well / Action Items. Common retro formats (Start/Stop/Continue, Glad/Sad/Mad, Liked/Lacked/Learned) have no home. The "Start Doing" concept — new ideas, practices from other teams — is an observation with no column.

**Decision:** 3 configurable reflection columns + 1 fixed Action Items column. The SM sets the reflection column names at sprint creation.

**Clarification on the model:**

Reflection columns are for observations — what the team noticed. Action Items are for commitments — what the team will do. "Start doing" is an observation ("we should try X"), not a commitment. It belongs in a reflection column. If the team decides to act on it, someone creates an action item.

**Rules:**
- The SM can name the three reflection columns at sprint creation. Free-text names, max 30 characters.
- Default column names: "Went Well" / "Didn't Go Well" / "Start Doing" (v1 defaults preserved for the first two, third column is new).
- Column order is fixed as entered (left to right = column 1, 2, 3, then Action Items rightmost).
- Columns cannot be added or removed beyond the 3+1 structure. This keeps the UI predictable and avoids the "template engine" rabbit hole.
- Column names are stored per sprint, not per team. Different sprints in the same team can use different column names.

**Data model impact:**
- `Sprint` table gains: `Column1Name`, `Column2Name`, `Column3Name` (string, max 30, with defaults "Went Well", "Didn't Go Well", "Start Doing").
- `Card.ColumnType` enum changes from `WentWell / DidntGoWell / ActionItems` to `Column1 / Column2 / Column3 / ActionItems`. The semantic meaning is defined by the sprint's column names, not the enum value.
- Data migration for existing v1 cards: `WentWell` -> `Column1`, `DidntGoWell` -> `Column2`, `ActionItems` -> `ActionItems` (unchanged).

**UX:**
- Sprint creation form includes three text inputs for column names, pre-filled with defaults.
- On the sprint board, column headers display the custom names.
- Action Items column header is always "Action Items" — not editable.

**Common mappings (for reference, not enforced):**

| Template | Column 1 | Column 2 | Column 3 |
|----------|----------|----------|----------|
| Default | Went Well | Didn't Go Well | Start Doing |
| Classic | Keep Doing | Stop Doing | Start Doing |
| Emotional | Glad | Sad | Mad |
| 3L | Liked | Lacked | Learned |

### 4.5 Inline Phase Controls

**Problem:** In v1, the SM must navigate back to the sprint manager page to advance the phase. This breaks flow during a live retro.

**Decision:** Move phase controls into the sprint board view. Phase advancement happens inline where the action is.

**Phase sequence (unchanged from v1):** Writing -> Grouping -> Voting -> Discussing -> Reporting.

All 5 phases are represented in the controls. "Close Sprint" is a separate action — it transitions the sprint **state** (Active -> Closed), not the phase. These are independent machines.

**Participant readiness indicator:**
- During Writing and Voting phases, the top bar shows a readiness badge: `4/6 done`.
- Participants signal readiness by clicking an "I'm done" button (visible during Writing and Voting only).
- The badge is informational — it does not block the SM from advancing. Its purpose is to give the SM visibility into pacing so they don't cut people off or wait too long.
- Readiness state is ephemeral (SignalR group state, not persisted). Resets on phase advance.
- Non-applicable phases (Grouping, Discussing, Reporting) show no readiness indicator.

**Advance confirmation dialogs:**
- All phase transitions show a confirmation dialog (existing v1 behavior from #21).
- **Voting → Discussing** adds context: "N participants haven't voted yet — advance anyway?" The count comes from comparing participants who have cast at least one vote vs. total active participants. This is a soft warning, not a hard block — the SM can always proceed.
- **Discussing → Reporting** preserves the existing gate: at least 2 discussed groups required. Backend enforces with 409; frontend shows confirmation dialog with count.

**UX:**
- Top bar on the sprint board shows: current phase name + readiness badge (Writing/Voting only) + "Next: {phase}" button (right-aligned).
- Visible to all participants (so everyone knows what phase they're in). Actionable only by the SM.
- Non-SM participants see the phase indicator and readiness badge but no advance button.
- The "Close Sprint" button appears separately (not as a phase advance) when the sprint is in the Reporting phase. Confirmation dialog: "Close this sprint? No more changes will be allowed."
- Phase transitions continue to be pushed via SignalR to all participants in real-time (existing v1 behavior).

**What stays on the sprint manager page:** Sprint creation, sprint list, sprint settings (name, date). Phase advancement and sprint closure move out.

### 4.6 Timer per Phase

**Problem:** Retros run long. Without timers, the SM has to use a phone timer or just wing it.

**Decision:** Optional countdown timer for applicable phases, controlled by the SM.

**Applicable phases:**
- **Writing:** default 5 minutes
- **Voting:** default 3 minutes
- **Discussing:** default 10 minutes
- **Grouping:** no timer (SM-only phase, pacing is self-evident)
- **Reporting:** no timer (terminal phase, read-only)

**Rules:**
- The SM can start a timer at any point during an applicable phase. Not required — phases can run untimed.
- Timer is visible to all participants in real-time (SignalR broadcast).
- When the timer hits zero: visual + optional audio alert. The phase does NOT auto-advance — the SM decides when to move on.
- The SM can: start, pause, reset, or add time (+1 min, +2 min, +5 min).
- Default durations are configurable per sprint at creation.

**Data model impact:** Minimal. Timer state is ephemeral — managed in memory on the server via SignalR group state. No persistence needed. Default durations are stored as a JSON column on `Sprint` (`TimerDefaults`).

**UX:**
- Timer appears in the top bar next to the phase controls (§4.5).
- Compact display: `03:42` countdown. SM sees start/pause/reset/+time controls. Participants see the countdown only.
- Timer expiry: the countdown flashes red, optional browser notification sound (respect mute preference).
- In Grouping and Reporting phases, no timer controls are shown.

### 4.7 Open Actions from Previous Retro

**Problem:** Retros should start by reviewing what was committed last time. Currently there's no connection between sprints — each retro starts from zero.

**Decision:** At the start of a new sprint's retro (Writing phase), show action items from the most recent closed sprint in the same team. The SM can mark each as Done, Carried Over, or Dropped.

**Rules:**
- Only action items from the previous closed sprint are shown.
- "Previous sprint" = the most recently closed sprint in the same team, by `ClosedAt` timestamp.
- If there's no previous sprint (first retro), this section doesn't appear.
- The review happens inline at the top of the sprint board during the Writing phase — not a separate step or phase.
- Status updates (Done / Carried Over / Dropped) are persisted on the original action item card in the previous sprint, not copied into the new sprint.

**Data model impact:**
- `Card` table gains a `ReviewStatus` enum column: `None` (default), `Done`, `CarriedOver`, `Dropped`. Only meaningful for cards where `CardType = ActionItem`.
- `Card` table gains a `ReviewedInSprintId` nullable FK — which sprint reviewed this action item. Enables cross-sprint traceability without duplicating cards.

**UX:**
- Collapsible section at the top of the sprint board: "Actions from last sprint ({count})".
- Each action item shows: text, assignee, and three status buttons (Done / Carried Over / Dropped).
- SM-only interaction. Participants can see the section but not change statuses.
- Once all items are reviewed, the section collapses and stays collapsed. Can be re-expanded.

**Why not copy actions into the new sprint:** Copying creates duplication and data integrity issues. The action lives in its original sprint; the new sprint merely references and reviews it.

|-------|--------|---------|
| `User` | **New table**: Id, Email (unique), Name, GivenName, CreatedAt | §4.0 (User entity) |

| `Participant` | Add nullable `UserId` FK to `User` | §4.3 (Dual auth) |

**Migration dependency:** §4.0 must migrate first. It creates the User table that §4.1 and §4.3 depend on. The remaining migrations are independent of each other.

## 6. What's Explicitly NOT in V2

- **Agent-authored cards** -> v3. Requires memory layer.
- **Memory layer / context store** -> v3. Separate service, significant investment.
- **Jira API integration** -> v3. Evidence links remain URL-based with OpenGraph fetch.
- **Cross-sprint analytics** -> v3. Trend detection, recurring themes.
- **Phase revert / undo accidental advance** -> backlog #22, evaluate after real usage.
- **Card comments / discussion threads** -> maybe v3. Not essential for a live retro.
- **Custom retro templates (beyond column names)** -> not planned. Column naming covers 90% of the need.
- **Presentation mode** -> not planned. The SM drives discussion verbally.
- **Card masking (hide-then-reveal)** -> not planned. Cards are already anonymous.
- **Emoji reactions / kudos** -> not planned. Nice-to-have, not a gap.
- **Icebreaker questions** -> not planned. Low value.

## 7. Decision Log

| Decision | Reasoning |
|----------|-----------|
| User entity as step 0 | V1's `CreatorEmail` string is a workaround. Proper FK relationships are prerequisite for multi-team and dual-auth. Do it right, not around it. |
| Both Google + Guest participant paths | Participants are invited via a link. They choose how to join — Google for persistent identity, guest for zero-friction entry. Neither path is privileged. |
| Hard delete on team deletion | Lightweight tool, not enterprise. No audit trail requirement. |
| Type-to-confirm on team delete | Prevents accidental deletion. Standard UX pattern. |
| Cannot delete team with active sprint | Prevents data loss mid-retro. |
| Phase controls inline, not separate page | Every competitor does this. The separate page was a v1 shortcut that created SM friction. |
| Close Sprint is separate from phase advance | Sprint state and phase are independent machines (v1 design). Close Sprint is a state transition, not a phase advance. |
| Timer does not auto-advance phases | The SM decides when to move on. Auto-advance would cut off participants mid-thought. |
| No timer for Grouping or Reporting | Grouping is SM-only, pacing is self-evident. Reporting is terminal and read-only. |
| 3 configurable + 1 fixed Action Items | Covers common retro formats without building a template engine. Action Items is structurally different (assignee, no voting). |
| Column defaults = v1 names | "Went Well" / "Didn't Go Well" are the established defaults. Third column "Start Doing" is new. |
| Column names per sprint, not per team | Different retros may use different formats. Per-sprint gives flexibility with zero extra complexity. |
| Positional ColumnType enum | Semantic values (`WentWell`, `DidntGoWell`) break when columns are renamed. Positional values (`Column1`, `Column2`, `Column3`) are stable. Migration happens as part of the configurable columns feature. |
| Review actions from previous sprint, not copy | Copying creates duplication and data integrity issues. The action lives in its original sprint; the new sprint references it. |
| Timer state is ephemeral | Timer is a live facilitation tool. No value in persisting mid-timer state. Default durations are persisted on Sprint for convenience. |
| Readiness indicator is soft, not a gate | Competitor research (Retrium, TeamRetro, Parabol, Neatro) shows hard gates create friction when participants are AFK or disengaged. A soft "4/6 done" badge gives the SM visibility without blocking the retro. |
| Voting completion warning, not hard block | Retrium hard-blocks on vote completion; TeamRetro makes it configurable. We chose a soft warning ("N haven't voted — advance anyway?") because hard blocks let a single AFK participant stall the entire retro. The SM always has the final call. |
